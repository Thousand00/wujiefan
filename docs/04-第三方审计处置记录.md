## 2. P1 逐条：问题、根因、修法

### P1-1 热键设了，重启后消失

**报告的链路是对的**，我按它走了一遍源码确认：

1. `HotKeyCombo.ToSettingString()` 对白名单外的键退回 `"0x" + vk.ToString("X2")`；
2. `TryParse` 只查 `s_nameToVk` 名字表，**不认十六进制**；
3. 于是 `Ctrl+0x2C`（PrintScreen）存得进 `settings.json`，读不回来；
4. `AppSettings.Load()` 解析失败即 `StrongCoolHotKey = ""`；
5. `MainForm.ApplyHotKey()` 还忽略了 `TryParse` 的返回值。

用户看到的现象是三步递进：设了 → 当时不生效 → 重启后键位没了，全程没有一句提示。触发键是 PrintScreen / CapsLock / NumLock / Pause / Apps / 小键盘加减 —— 都不是冷门键。

**修法（两层，缺一不可）**

- 解析器认 `0xXX` 写法（新增 `TryReadKey`，先查名字表再认十六进制，范围 1..0xFF）。这样**存得进去就一定读得回来**，往返恒等由结构保证，不靠白名单完备。
- 白名单补 8 个常见键（PrintScreen / CapsLock / NumLock / ScrollLock / Pause / Apps / NumPlus / NumMinus），让常见键存成可读文本而不是十六进制。
- 新增 `IsRepresentable(int)` 供界面判断。
- `ApplyHotKey` 遇到无法识别的写法时**只停用并说明，不再清空设置**。

**验证**：新增 3 组测试 —— 1..0xFF 全扫往返（`IsRepresentable` 为真者必须能解析回同一 VK，且规范化幂等）、8 个新白名单键的名字里不含 `0x`、十六进制写法三种大小写形态都能解析。另加非法十六进制被拒（`0x00` / `0x100` / `0xZZ`）。

### P1-2 读失败时不发帧，覆盖层停在旧数

原代码在失败分支 `_mode()?.CheckReadError()` 之后就 `return`，`_publisher.Publish()` 只在成功路径上。EC 掉线、休眠恢复期间，RTSS 上一直显示几分钟前的温度和转速。

**为什么这条归 P1**：温度是过热保护唯一的安全信号。显示一个陈旧的「68°C」和显示「无数据」在安全性上完全相反 —— 前者让人以为一切正常。

**修法**：失败时卡片置 `--`；新增 `RtssPublisher.PublishUnavailable()`，它记住上一次的槽位 Id+Label，发布「槽位都在、值全空」的帧，RTSS 显示无效值而不是旧值。记住槽位是关键 —— 不记的话 RTSS 那几个 overlay 条目会整个消失再出现。

### P1-3 自启查询两次，瞬时失败会删掉已有任务

`OpenSettings` 先查一次展示状态、决策时再查一次；而 `IsEnabled()` 把「查询失败」与「没有任务」压成同一个 `false`。两次查询之间只要抖动一次，就会出现：

> 界面显示「关闭」→ 用户点保存 → 程序判定「需要关闭」→ `Disable()` 删掉一个本来正常的任务。

**修法**：`AutoStartManager` 新增四态 `QueryState()`，返回 `Unknown / Absent / Ours / Foreign`。`Unknown` 时锁住该行并写清原因（「查询计划任务失败, 已锁定」）；整个保存流程**只查一次、复用结果**，决策不再二次调用 schtasks。

### P1-4 schtasks 超时形同虚设

原实现：

```csharp
Task<byte[]> errTask = ReadAllBytesAsync(p.StandardError.BaseStream);
byte[] outBytes = ReadAllBytes(p.StandardOutput.BaseStream);   // 同步读到 EOF
if (!p.WaitForExit(15000)) { ... }                            // 排在后面
```

同步读在前，15 秒超时在后。进程挂住不关 stdout，`ReadAllBytes` 永不返回，超时永远轮不到执行。

**叠加问题更实际**：启动路径上最多四次串行 schtasks（`HasForeignTask` + `IsEnabled` + `IsUpToDate` 内部再两次），全在 UI 线程，白屏几百毫秒到一秒。

**修法**：两流都异步读 → 先 `WaitForExit(15000)` → 超时即 `Kill()` 并返回错误 → 再以 2 秒上限把已读到的缓冲收回来（`ReadWithTimeout`）。启动路径收敛为一次 `QueryState()`。

### P1-5 关机时 Unknown 直接放弃

```csharp
if (before is FanModeState.Auto or FanModeState.Unknown) return;   // 改前
```

读不出状态就不收手。但**读不出来恰恰等于无法确认它是干净的**，而写 Auto 是幂等的 —— 该写。

**修法**：只在确认 `Auto` 时跳过，`Mixed` 与 `Unknown` 都写一次 Auto。同时加 `Interlocked.Exchange` 一次性标志：关机事件（SystemEvents 回调线程）与 Dispose（UI 线程）都会调它，重入会多写一遍，还可能让后一次读到前一次写了一半的中间态而误报「状态不确定」。

三条值得单独说：

**P2-8 是「报错原因不真实」而不是「安全被绕过」。** 大小不符的文件 `continue` 跳过、没计入 `compared`，于是「无交集」分支先命中，把「整包大小全对不上」报成「清单损坏」。两种都不会进后台，效果一样 —— 但排查时会被引到完全错误的方向。

**P2-9 与 P1-2 是一对。** 报告说「空快照整帧不发」，实际代码是 `Marshal.Copy` 零填充写入 —— 那是**主动清空**，比不发更糟，而注释写的正是「整帧不发」。也就是说注释和代码是反的，我按实际行为改代码、并重写注释。P1-2 管「发什么」，P2-9 管「空的时候不要毁掉已有的」。

**P2-14 释放共享系统图标。** `LoadAppIcon` 兜底 `return Icon.ExtractAssociatedIcon(...) ?? SystemIcons.Application;`，而 `Dispose()` 无条件释放图标 —— `SystemIcons.Application` 是进程内共享静态实例，释放等于把 .NET 自己的句柄销毁了。改为返回 `Clone()`。

## 6. 我不同意报告的地方

报告末尾有 4 条「经核实不是 bug」，**我全部同意**，其中一条想补充理由：

**AIDA 共享内存的撕裂风险。** 报告说「单次 `Marshal.Copy` 的撕裂风险已论证」。我这边有实测数据支持：1Hz 发布节奏下 1790 万次读 **0 次撕裂**；更关键的是，800↔1200（变长）与 800↔900（等长）两组压测共约 1600 万次读，**从未出现任何从未被写入过的合成数值** —— 也就是说不会显示「看似合法但错误」的转速。曾经试过 seqlock（先清零首字节 → 改写正文 → 单字节写回首字节），结果撕裂从 46 次/40 万读**恶化到 8,803 次**（191 倍），因为把一次 memcpy 拆成多次反而拉长了窗口。这条路已评估并否决。

另外三条（RTSS 侧 `Rpm.ToString()` 不是区域性 bug、Win 键已用 `GetAsyncKeyState` 补读、`0xA5/0xCC` 会被 EC 在 1.5 秒内回滚）我也核对过，同意。

**需要更正的一处**：报告 P3-25 说「CI 缺失」，实际 CI 已经在跑（`.github/workflows/ci.yml`），只是缺 CA 与 `-warnaserror`。

### EcMutex 这 6 条为什么值得单说

这个类出错的样子特别隐蔽：锁没还干净，HWiNFO / LibreHardwareMonitor 从此读不到 EC，而**本程序一切正常** —— 用户只会发现「装了 WujieFan 之后 AIDA 读不到风扇了」。代码注释里记着这条历史缺陷，而它此前零覆盖。

要测它得先解决两件事：

1. **不能碰真实的 `Global\Access_*` 锁名。** 测试一失败就顺手把用户的 EC 访问锁死，等于用弄坏环境来验证代码。给 `EcMutex` 与 `AidaSharedMemory` 都加了可注入名字的构造（与之前 `IEcTransport` 的做法一致），测试走 `Local\WujieFanTests_<pid>_<guid>`。
2. **Win32 互斥量的归属是线程。** `Acquire` / `Release` 必须在同一线程上完成。第一版用 `Task.Run(...).Result` 跨线程取放，还踩了 `TaskCompletionSource` 不能 `using`（`CS1674`）与 7 条 `xUnit1031`。

最要紧的坑：**竞争方不能用线程池**。线程池可能把工作项安排到调用者正在使用的线程上，而同一线程对同一把互斥量是**可递归**的 —— 那样测出来的「别人也能拿到」其实是自己拿到了。第一版因此 5 次跑 3 次红。改成独占 `new Thread` + 断言线程号确实不同，连跑 5 轮全绿。
