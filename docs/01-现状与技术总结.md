## 0. 一句话现状

- **目标已达成**：两个风扇转速现在是 RTSS OverlayEditor 布局里**可拖动、可编辑的图层**（Layer35 / Layer36），与 CPU 温度那些原生元素同构。

### 2.2 固件布局
| 偏移 | 内容 |
|---|---|
| 0x000000–0x05FFFF | ITE EC-V14.6 8051 固件（IP3TECH___P0/P1） |
| 0x0C1000 | PSP 目录 |
| 0x541F00–0x9D0F00 | AMD 微码 |
| 0x1000000–0x19B0000 | AMI AptioV BIOS |
| 0x19C0000+ | NVRAM / BootBlock |

### 2.3 风扇表
- Fan1 表 @ ROM 0x2ECB，Fan2 表 @ ROM 0x2F25，每块 0x5A(90) 字节。
- 表内偏移：

| 偏移 | 内容 |
|---|---|
| +0x00 | T1[15] 降温阈值 |
| +0x0F | 间隔字节 = 54 |
| +0x10 | T2[14] 升温阈值 |
| +0x1E | PWM[15] |
| +0x2D | RPM[15]（×100） |
| +0x3C | E[15] |
| +0x4B | F[15] |

- 原厂 PWM：Fan1 = 47,75,86,97,111,127,140,153,173（最高 67.8%）；Fan2 = 39,65,73,83,97,120,129,136,150,162（最高 63.5%）。
- T1 = 0,53,58,63,69,75,81,92,97；T2 = 55,60,66,72,78,84,95,99,FF…

### 2.4 PWM 的关键物理约束
- **PWM 有效范围 0–184**。184 = 100% 占空比 = **5720 rpm 物理上限**。
- **大于 184 的值会让风扇直接停转**（实测 200 / 220 / 240 / 255 全部 RPM=0）。
- RPM 近似线性：约 **27.7 RPM / PWM 单位**（PWM 40 → 1727 rpm，184 → 5719 rpm）。
- 硬件寄存器：PWM 周期 0x1801 / 0x1803 = 0xB8(184)；duty 0x1804(Fan2) / 0x1809(Fan1)。

### 2.5 已验证的 EC 通道（I2EC）
- 端口基址：**0x4E（I2EC 使能）** 或 0x2E（备用，实测在此机型上读到垃圾值，**不要用**）。
- 访问方式：_sel 写索引 → _commit 触发 → 读数据口。这套实现目前**重复了 4 份**（原仓库的 daemons 与 tools 里），本项目只保留一份。
- 温度无法从 EC 内部 XRAM 0x9600 读到（I2EC 寻址只到 0x7FFF），**主机侧必须读 0x0470**。

## 3. 本项目用到的 EC 寄存器表（fanprobe.py 已实现并实测）

| 用途 | Fan1 | Fan2 | 说明 |
|---|---|---|---|
| 转速 TACH | 0x181E / 0x181F | 0x1820 / 0x1821 | 两字节，需稳定读取 |
| PWM 硬件输出 | 0x1809 | 0x1804 | 实际占空比 |
| PWM 当前值 | 0x0215 | 0x0295 | |
| PWM 目标值 | 0x0214 | 0x0294 | |
| 档位等级 | 0x0213 | 0x0293 | 实测 2–5 |
| 模式标志 | 0x021F | 0x029F | 见下 |
| 温度 | — | — | 0x0470（CPUT，全局共用） |

**换算常数** TACH_CONST = 2156250（RPM = TACH_CONST / count，或按实测标定）。

**模式标志取值**
| 值 | 含义 |
|---|---|
| 0x00 | 自动（EC 固件控制） |
| 0xA5 | 自定义曲线 |
| 0xCC | 自定义温度（温度改由 0x021E 提供） |
| 0xDC | 手动 PWM 直通 |

> 0xDC 是**唯一稳定可用**的自定义模式；其余模式在实测中会被 EC 固件在 1.5 秒内回写覆盖。

### 3.1 已证伪的传言（不要再试）
原仓库做过 7 项实验证伪，结论可靠：
- **充电限制 BCTH/BCTL（0x494/0x495）在 EC 固件里零引用 → 纯摆设，改了没用。**
- **80% 电池维护状态机（@ROM 0x10B1E）是死代码**：0x581 bit5 会在 1.5 秒内被回写为 0；LIDF 写 0xFF 回读 0xF8；计时器 3 秒内被复位为 1。

## 4. 读取风扇转速：已完成的工具

### 4.1 fanprobe.py（位于原仓库 E:\WORKS\mechrevo-wujie14-ec-master\Win11\）
- 单文件约 25KB，**只用标准库 + ctypes**，无第三方依赖。
- 通过 **PawnIO** 驱动做端口 I/O（LpcIO.bin 模块的 ioctl_select_slot / ioctl_pio_inb / ioctl_pio_outb）。
- **必须管理员权限**：PawnIO 设备 SDDL 是 D:P(A;;GA;;;SY)(A;;GA;;;BA)，只有 SYSTEM 与 Administrators 能打开。
- 内置 UAC 自提权（_relaunch_elevated），父进程负责写 --out 文件。

- 实测读数：温度 64–84 °C；Fan1 3300–4200 rpm；Fan2 2900–4000 rpm；20 次采样抖动小于 1%。

## 5. 屏幕上的风扇数字到底从哪来（已查实，勿再猜）

### 5.1 结论
**RTSS 自己不读 EC**。屏幕上的风扇数字来自 **WujieFan**：它创建 `AIDA64_SensorValues` 共享内存并写入 AIDA 格式 XML，OverlayEditor 经 AIDA 数据源通道取走，渲染成 Layer35 / Layer36。

实测链路（2026-11-14 07:52，同一秒）：

    共享内存  <fan><id>WUJIE_FAN1</id><label>Fan1 (CPU)</label><value>3483</value></fan>
              <fan><id>WUJIE_FAN2</id><label>Fan2 (GPU)</label><value>3075</value></fan>
    图层渲染  <P=0,-4><L35><C4>Fan1 3483 RPM<C><P=-120,-4><L36><C11>Fan2 3075 RPM<C>

> 历史说明（防止重蹈覆辙）：在 WujieFan 之前，数字由 `fanprobe.py --watch --rtss` 写进 **1 号 OSD 槽**（owner=`WujieFanProbe`，见 fanprobe.py:603 与 :628）。那条路**不可拖动**，已废弃。两代实现共用同一个洞察：RTSS 允许外部进程喂数据。

### 5.2 为什么 OverlayEditor 里那两个风扇元素选不中
RTSS 有**两条完全独立的渲染通道**：

| | OSD 槽通道 | OverlayEditor 布局通道 |
|---|---|---|
| 载体 | RTSSSharedMemoryV2 里 8 个 OSD 槽 | .ovl 文件 + 2 号槽 |
| 内容 | 纯文本（可带 <C>/<S> 简单标签） | 富文本 <FNT> / <L> / <OBJ>，Layer 化 |
| 谁能写 | 任何进程 | 只有 OverlayEditor |
| 可否拖动编辑 | **不可以** | **可以** |
| 我们的风扇数字 | 在这里 | 不在这里 |

OverlayEditor **只认自己 .ovl 里的 Layer**，根本不知道 1 号槽被别的程序占了 —— 所以屏幕上看得见风扇数字，但编辑器里找不到、点不中。

### 5.3 已作废的错误结论（记录下来防止重蹈覆辙）
曾经推断：「风扇数字来自 RTSS HAL 的 GPU 风扇通道 0x230/0x231，AMD ADL 在 APU 上把它转发成平台风扇」。
**这个结论是错的**，已被推翻。推翻依据：
- HAL 只有 GPU 风扇 ID（GPU_FAN_SPEED 0x230 / GPU_FAN_SPEED_RPM 0x231），**没有任何笔记本/主板风扇 ID**。
- default.ovl 里 106 个数据源全部 Provider=HAL，**唯一的 RPM 源 [Source99] GPU1 fan tachometer 未被任何 Layer 引用**。
- AIDA64_SensorValues / MAHMSharedMemory / HWiNFO_SENS_SM2 三块共享内存当时全部 NOT_FOUND，排除 AIDA/MSIAB/HwInfo 通道。

## 7. OverlayEditor 数据 provider 全通道调研（核心调研成果）

源码根：C:\Program Files (x86)\RivaTuner Statistics Server\SDK\Plugins\Client\OverlayEditor\（完整源码随 RTSS 分发）

Provider 名常量（OverlayDataSource.h:9-16）：
PROVIDER_HAL "HAL" / PROVIDER_MSIAB "MSI Afterburner" / PROVIDER_HWINFO "HwInfo" / PROVIDER_AIDA "AIDA" / PROVIDER_PERFCOUNTER "PerfCounter" / PROVIDER_PRESENTMON "PresentMon" / PROVIDER_LHM "LHM" / PROVIDER_INTERNAL ""

### 7.1 通道一：AIDA64 共享内存 —— 唯一可行的"零侵入"通道

**机制（OverlayDataProviderAIDA.cpp:19-59）**

    OpenFileMapping(FILE_MAP_ALL_ACCESS, FALSE, "AIDA64_SensorValues")
      -> MapViewOfFile
      -> CString strCache = pMapAddr;      // 整块当 C 字符串
      -> AIDA64_ParseXML(strCache);
      -> InvalidateDirtySources();

**关键：它只看共享内存的名字，完全不校验是谁创建的。** → 任何进程创建同名内存，RTSS 就会读。

**XML 解析（AIDA64Parser.cpp:23-152）**
手写三态机：PARSER_STATE_VAL 0 / TAG_HEAD 1 / TAG_TAIL 2。
- TAG_HEAD/TAG_TAIL 里再遇到 "<" → 直接 return FALSE
- VAL 状态里遇到 ">" → 直接 FALSE
- 尾部标签与栈顶不 _stricmp 相等 → FALSE
- **不能写 <?xml ... ?> 声明**（"?" 会被当普通字符塞进 tag 名）
- 结尾**没有**「栈非空」校验（:151 直接 return TRUE），但按规矩还是严格闭合为妙

**元素处理（AIDA64Parser.cpp:154-195）**
- level 0 = 一个传感器整块：进来时若 id + value 都非空 → 调 AIDA64_ParseSensor()，然后清空三个累加器
- level 1 = 属性，**只认 id / label / value** 三个（_stricmp 不区分大小写）

**最小可解析 XML**

    <fan><id>F1</id><label>Fan1</label><value>3433</value></fan>
    <fan><id>F2</id><label>Fan2</label><value>3032</value></fan>
    <temp><id>T1</id><label>EC Temp</label><value>73</value></temp>

（顶层标签名决定显示类型，见 OverlayDataSourceAddDlg.cpp:234-241）

**类型 → 显示映射（OverlayDataSourceAddDlg.cpp:234-241，_stricmp 匹配）**
| 顶层标签 | 显示名 | 单位 |
|---|---|---|
| temp | Temperature | 摄氏度 |
| fan | **Fan tachometer** | **RPM** |
| duty | Fan speed | % |
| volt | Voltage | V |
| pwr | Power | W |

**取值**：OverlayDataProviderAIDA.cpp:66-110 → UpdateSource(lpID, lpValue) → sscanf_s(lpValue, "%f", &fltData)。ID 支持逗号分隔多值 + PathMatchSpec 通配（OverlayDataProvider.cpp:99-118）。

**持久化**：OverlayDataSourceAIDA.cpp:33-57 在 .ovl 的 [SourceN] 段里写 Provider=AIDA + ID=<我们给的 id>。

**这个通道不需要 MFC、不需要改 OverlayEditor.dll。** 唯一待解的问题是「谁持续写这块内存」。

### 7.2 通道二：HAL —— 已排除

## 8. 自写 RTSS 插件 DLL 这条路（已实验；根因已查清，未采用）

> 这条路**最终没有采用**——AIDA 通道已经达成目标，不需要 RTSS 进程内插件。但实验结论有价值，记录下来。

### 8.1 插件契约（以 HotkeyHandler 为模板，逐字核实）
路径 `SDK\Plugins\Client\HotkeyHandler\`
- 导出三个函数（`HotkeyHandler.def` 的 EXPORTS 段是**空的**，全靠 `__declspec(dllexport)`）：
  - `BOOL Start()` — 建一个隐藏宿主窗口
  - `void Stop()` — 销毁它
  - `BOOL Setup(HWND hWnd)` — `if (!hWnd) return TRUE;`
- **调用约定是 `__cdecl`**。`HotkeyHandler.h` 里 `#define HOTKEYHANDLER_API extern "C" __declspec(dllexport)` —— **没有 WINAPI**。
- **`Setup(NULL)` 只是能力探测，必须 return TRUE**。`HotkeyHandler.cpp:90` 注释原文："host will call Setup with hWnd set to NULL to verify if configuration is supported by plugin"。
- 宿主 API 从 `GetModuleHandle(NULL)` 用 `GetProcAddress` 取：`GetHostAppProperty` / `LocalizeWnd` / `LocalizeStr`（见 `SDK\Include\RTSSExports.h:27-46`）。

### 8.2 冒烟实验与真正的崩溃根因
- 源码/构建/部署脚本已归档到 `docs\archive\smoke-plugin\`（SmokePlugin.cpp / .def / build_smoke.bat / smoke.log）。
- 日志实测序列：`DLL_PROCESS_ATTACH` → `Setup(hWnd=00000000) called -> return TRUE` → `DLL_PROCESS_DETACH`。
  → RTSS 确实扫描、LoadLibrary、调用了 Setup(NULL)，**但紧接着 FreeLibrary**。
- 随后崩溃：`RTSS.exe 7.3.5.28314 / 0xc0000005 / Fault offset 0x000105c4`。
- **真正的根因：调用约定错了，不是缺 MFC。** 冒烟 DLL 用 `WINAPI`（__stdcall）声明带参的 `Setup(HWND)`，而宿主按 `__cdecl` 调用 → **双重清栈** → 栈失衡崩溃。
- 教训：早期记的「纯 Win32 DLL 必崩、必须 MFC」是**误判**。纯 Win32 插件只要改成 `__cdecl` 即可，无需 MFC。
- 已完整回滚，`PlugIns\Client\` 恢复原状，未留残留。

### 8.3 编译环境事实（若将来仍要走插件路）
- VS BuildTools **18.7.11919.86**，位于 `C:\Program Files (x86)\Microsoft Visual Studio\18\BuildTools`（**不是** 2022 路径）。
- MSVC 仅 `...\VC\Tools\MSVC\14.51.36231`；**atlmfc 目录不存在，全盘搜 afxwin.h = NONE** → 本机没有 MFC 头文件与库。
- 但 MFC **运行时**齐全（System32/SysWOW64 下 mfc140u.dll / mfc140.dll 等，14.50.35719.0）。
- → 能跑现成 MFC DLL，编不出 MFC 扩展 DLL；不过按 §8.2 的结论，这条路本来也不需要 MFC。

## 9A. WujieFan 程序实现（当前主程序）

### 9A.1 定位与形态
`src\WujieFan` + `src\WujieFan.Core`，C# / .NET 8 / WinForms / **仅 x64**。

为什么必须 x64：PawnIO 的 `PawnIOLib.dll` 与 `PawnIO.sys` 都是 x64，读 EC 的整条链路都在同一进程内，32 位进程加载不了。

`app.manifest` 写死 `requireAdministrator` —— 因为 PawnIO 设备对象 SDDL 是 `D:P(A;;GA;;;SY)(A;;GA;;;BA)`，只放行 SYSTEM 与 Administrators。

### 9A.2 启动与生命周期
- `Program.cs` 用 `Global\\WujieFan_SingleInstance` 互斥量保证单实例；已有实例时广播 `WujieFan_ShowWindow` 把它唤到前台再退出。**这条是必需的**：自启动与手动双击会同时触发。
- 支持 `--tray` 参数直接最小化到托盘（自启动用）。
- 关窗口默认缩到托盘（`AppSettings.MinimizeToTray`），从托盘菜单真正退出。

### 9A.3 读 EC（WujieFan.Core\Ec）
- `FanReader.Open()` 的顺序是刻意的：**先** `HardwareIdentity.Read()` + `SupportedHardware.Check()`，**不通过直接抛 `HardwareNotSupportedException`，根本不碰硬件**；通过后才 `new PawnIo()` → `EcMutex.Acquire(2000)` → `EcAccess.LoadModule(LpcIO.bin)` → `DetectPort()`。
  理由写在源码注释里：寄存器地址是特定固件逆向出来的，机型不符时读出来的数字**看着合理但完全错误**，宁可直接拒绝也不"尽力而为"。
- `FanReader.Read()` **不抛异常**，返回带 `Error` 的 `FanSample`，供界面持续刷新。
- 温度 `<1 or >100` 视为无效（null），避免把 0xFF 之类的越界值当成温度。
- 打开后复用同一个 PawnIO 句柄与端口，不反复探测，减少 I/O 抖动。

### 9A.4 机型校验（Hardware\SupportedHardware.cs）
白名单只有一条：`MECHREVO` + 机型名含 `WUJIE 14` / `WUJIE 14+` / `ARN39P`，且 **EC 固件必须精确是 2.12**。
拒绝时会给出 `Title` + 完整 `Detail`（说明为什么拒绝、支持哪些机型、怎么强制跳过），而不是简单报"打开失败"。

### 9A.5 供数（Providers\AidaSharedMemory.cs）
- 创建/复用 `AIDA64_SensorValues` 命名共享内存，64KB。
- 每次写入用**零填充缓冲区一次拷入**：本次数据 + null 结尾，同时把上次较长写入的残留覆盖为零，避免尾部脏字符。
- 任一风扇无有效读数时该条 `value` 留空 —— RTSS 会显示为无效值，而不是误显示 0。
- XML 严格遵守 §7.1 的解析器约束：无声明、无注释、无根节点、无自闭合标签。

### 9A.6 界面（Ui\MainForm.cs）
- `System.Windows.Forms.Timer` 定时采样，间隔 = `Clamp(PollIntervalMs, 200, 10000)`。
- 连续 5 次错误自动重连；`SystemEvents.PowerModeChanged` 在休眠恢复时也重连（EC 在睡眠后可能失效）。
- 两个勾选框：开机自启动、向 RTSS 提供数据。

### 9A.7 开机自启（Config\AutoStartManager.cs）
写的是**计划任务**（`WujieFan`），不是注册表 Run 键 —— 因为需要最高权限，而 Run 键无法提权。

自 0.2.0 起任务**以普通权限（`LeastPrivilege`）运行 `WujieFanLauncher.exe`**，由启动器经 UAC 提权拉起主程序，原因见 §9A.12。任务里 `<Command>` 指向的是启动器，不再是 `WujieFan.exe`。

`IsOurCommand` 必须从 `<Command>` 里正确取出可执行文件路径再比较：任务命令行可能形如 `"E:\...\WujieFan.exe" --tray`，早期版本只 `Trim('"')` 去掉开头引号，残留的尾部引号与参数污染了路径比较，导致**启用后勾选仍然回弹**。现改为 `ExtractExecutable()` 精确截取。0.2.0 起还要**同时认启动器路径与主程序路径**，否则 0.1.x 遗留任务会被判成「别人的任务」，既关不掉也升不了级。

`IsUpToDate()` 里有两个「节点会被省略」的陷阱（见 §13 第 42 条）：`ExecutionTimeLimit` 等于默认 `PT72H`、`RunLevel` 等于默认 `LeastPrivilege` 时，`schtasks /Query /XML` **根本不输出该节点**。判据必须写成「节点缺失 == 默认值 == 通过」，否则 `IsUpToDate()` 恒为 false，每次启动都白跑一遍 `schtasks` 重写任务。

### 9A.8 设置
`%LOCALAPPDATA%\WujieFan\settings.json`，字段 `PollIntervalMs` / `MinimizeToTray` / `PublishToRtss` / `ForceUnsupported` /
`EmergencyTemperatureC` / `EmergencyHoldSamples`，另有结构版本 `SchemaVersion`（缺失视为 0，即 0.4.0 及更早写的文件）。
读写全部 try/catch 静默降级 —— 配置坏了就用默认值，绝不因为读配置失败而让程序起不来。
降级时的默认值刻意选「不接管风扇」；越界的过热保护参数**回出厂默认而非夹到边界**，理由见 §14B。

### 9A.9 托盘与单实例唤醒（Ui\MainForm.cs + Program.cs）

**托盘**：`NotifyIcon` 在 `OnFormLoad` 第一行创建（`Icon` 从嵌入资源 `WujieFan.wujiefan.ico` 取，`Text` 是程序名）。双击 = `RestoreFromTray()`；右键菜单 = 「显示主窗口」+「退出 WujieFan」。

点 × 不退出，而是 `e.Cancel = true` 然后收进托盘。这里有两个必须知道的 Windows 语义：
1. **不能在 `FormClosing` 里直接改 `ShowInTaskbar`** —— 那会重建窗口句柄，使本次「取消关闭」失效，进程会被真的杀掉。必须 `BeginInvoke(new Action(HideToTray))` 把隐藏动作推到关闭流程之后。
2. 隐藏顺序是 `WindowState = Minimized` → `Hide()` → `ShowInTaskbar = false`，并且用 `_hidingToTray` 标志挡住 `WindowState` 变化引发的 `Resize` 重入。

**单实例唤醒**：早期用 `PostMessage(HWND_BROADCAST, RegisterWindowMessage(...))`，实测广播 `ok=True` 但目标进程收不到 —— **两个进程都是提权的，UIPI 会拦下广播消息**。现改为命名事件：
- 主实例：`new EventWaitHandle(false, EventResetMode.AutoReset, @"Global\WujieFan_ShowWindow")`，另起一个后台线程 `WaitHandle.WaitAny(new WaitHandle[]{wake, closed})`；收到信号后 `form.BeginInvoke(new Action(form.RestoreFromTray))`。
- 二次实例：`EventWaitHandle.OpenExisting(...)` + `Set()` 然后退出。捕获 `WaitHandleCannotBeOpenedException`（主实例还没建好事件）时也直接退出，绝不开第二个窗口。

**注意 `RestoreFromTray()` 必须是 `public`**：它在 `Program.StartWakeListener` 里被跨类调用。

参考实现：`src\WujieFan\Program.cs`（`StartWakeListener`）与 `src\WujieFan\Ui\MainForm.cs`（`CreateTrayIcon` / `BuildTrayMenu` / `HideToTray` / `RestoreFromTray` / `OnFormClosing`）。

### 9A.10 图层坐标语义（重要，踩过坑）

`.ovl` 里的 `PositionX` / `PositionY` **不是相对窗口左上角的绝对像素**。实测结论：
- `x` 是沿当前文字流的**推进量**，**负值向右**；`y` 是行偏移，**负值向下**。
- 数值过大会把图层推到渲染区域外，**不是报错，而是完全看不见**。`PositionX=-120` 时 Fan2 从未出现过；改成 `-16` 后与 Fan1 并排正常显示。
- 图层文本进的是 `<P=x,y><Lnn><Cn>文字<C>` 这类富文本标签流，与其余 35 个原生图层同构 —— 所以它是**可拖动编辑的标准图层**，不是 OSD 文本框。

验证手段：改完 `.ovl` 必须**重启 RTSS**（源码里没有热重载），然后用 `tools\peek-overlay.py --full` 看 `RTSSSharedMemoryV2` 1 号槽里 `RTSSOverlayEditor` 实际拼出的文本，再截图确认屏幕落点。

### 9A.11 本轮 bug 排查与修复清单（2026-11-14）

用户要求「检查一下还有没有bug」。逐行通读全部 15 个源文件与 3 个 Python 脚本，共修掉 15 处真实缺陷。按严重程度排：

#### 会让功能整段失效的（3 处）
1. **供数永久停掉且无提示**（`Ui\MainForm.cs` `OnTick`）。Publish 失败时原本 `_aida.Dispose(); _aida = null;`，注释说「让下一轮重建」，但 `OnTick` 从不调用 `ApplyPublishMode`（只在 `OpenReader` 成功、休眠恢复、改勾选时调）→ 一次写共享内存失败后 RTSS 里风扇数字**永久停在旧值或消失**。修复：`OnTick` 里按 10 秒退避重试重建（`_lastAidaTryTicks` / `AidaRetryIntervalTicks`）。
2. **旧自启动任务永不升级**（`Ui\MainForm.cs` `OnFormLoad`）。回填界面只调 `IsEnabled()`，任务已存在时 `Enable()` 根本不会被调用 → 0.1.0 建的旧任务（拔电源不启动、72 小时被杀）永远是旧定义。修复：`if (enabled && !_autoStart.IsUpToDate()) Enable();` 追加自动重写。
3. **schtasks 输出编码不定导致自启动识别失败**（`Config\AutoStartManager.cs` `Run`）。`schtasks /Query /XML` 的控制台输出**同一台机器上会在 UTF-8 与 GBK 之间变**；固定按任一编码解码，安装目录含中文时 `IsOurCommand` 永远匹配失败，勾选永远回弹「未启用」，连带 `Disable()` 也拒绝删除（以为是别人的任务）。修复：按**原始字节**读（`ReadAllBytes`），先严格 UTF-8（`throwOnInvalidBytes: true`）再退回系统 ANSI 代码页（`Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)` + `Encoding.GetEncoding(0)`）。

#### 会独占系统资源 / 泄漏的（3 处）
4. **EcMutex 全生命周期持锁**（`Ec\EcMutex.cs`）。原实现 `Acquire` 一次拿两把锁直到 `Dispose` 才释放 —— 采样间隔 1 秒期间一直占着 `Global\Access_ISABUS.HTP.Method` 与 `Global\Access_EC`，让 HWiNFO / LibreHardwareMonitor 拿不到 EC。已重写为**作用域锁**：`Acquire(timeout)` / `Release()` 成对调用，`FanReader.Read()` 每次采样成对获取。另修 `_acquired = true` 无条件置位（部分超时也算成功）的缺陷。
5. **PawnIo 构造失败泄漏模块句柄**（`Native\PawnIo.cs`）。版本校验失败或 `_open` 返回失败时直接 throw，`_hModule` 不释放 —— 每次重连失败泄漏一次 DLL 引用计数。修复：把「版本校验 + open」整段包进 `try/catch`，catch 里 `Dispose(); throw;`。
6. **schtasks 调用死锁**（`Config\AutoStartManager.cs` `Run`）。原本顺序 `StandardOutput.ReadToEnd()` 再 `StandardError.ReadToEnd()`：子进程把 stderr 缓冲写满就停住，父进程在等 stdout 关闭 → 死锁；且 `WaitForExit(15000)` 超时后进程不终止。修复：stderr 先起 `ReadToEndAsync()` 任务，超时 `Kill(entireProcessTree: true)`。

#### 会让程序变成「隐身」或崩溃的（4 处）
7. **没有托盘图标却仍然隐藏窗口**（`Ui\MainForm.cs`）。早期 `HideToTray()` 只改可见性，从没建过 `NotifyIcon`（grep NotifyIcon 零命中）→ 点 × 后窗口彻底消失，只能任务管理器杀。修复：`CreateTrayIcon()` 整体 try/catch，失败时 `_settings.MinimizeToTray = false` 且 `OnFormClosing` / `HideToTray` 双重守卫 `_trayIcon is null` 就**不隐藏**。
8. **唤醒监听线程会被一次异常永久关掉**（`Program.cs` `StartWakeListener`）。`catch (InvalidOperationException) { return; }` —— 句柄还没建好时那次唤醒白丢，并且线程直接退出，之后双击 exe 再也叫不回窗口。修复：先短等句柄（50 × 20ms），`ObjectDisposedException` 才 return，`InvalidOperationException` 改 `continue`。
9. **机型不受支持时每秒弹一个对话框**（`Ui\MainForm.cs`）。定时器每秒重试 `OpenReader()`，每次都弹 MessageBox。修复：新增 `_giveUpOpening` 标志 + `OpenReader(bool interactive = true)` 参数，只有用户主动拒绝才算放弃（自动重连失败不放弃）。
10. **休眠恢复回调跨线程操作控件**（`Ui\MainForm.cs` `OnPowerModeChanged`）。`SystemEvents.PowerModeChanged` 在系统事件线程触发，原代码直接动控件。修复：`BeginInvoke` 到 UI 线程 + `_disposedUi` 守卫挡晚到回调。

#### 数据正确性与脚本安全（5 处）

### 9A.12 开机自启后托盘图标不出现：计划任务的 job UI 限制（0.2.0 修复）

**现象**：手动双击 `WujieFan.exe` 一切正常、托盘图标在；改成由计划任务（登录触发）拉起后，进程活着、EC 读数正常、RTSS 供数正常，**但通知区域里永远没有图标**，点 × 收进托盘后只能去任务管理器杀进程。

**排查过程**（每一步都有实测日志）：

| 步骤 | 结果 | 结论 |
|---|---|---|
| 窗口站 / 桌面 / 完整性级别 | 计划任务与手动完全相同（`WinSta0\\Default`、`integrity=High`） | 排除 |
| 工作目录（`system32` vs 安装目录） | 两种都正常出图标 | 排除 |
| 任务 `RunLevel` Highest vs Limited | **两种都不出图标** | 与提权无关 |
| 经 `powershell` 中转再拉起 | 仍然不出 | 排除命令行差异 |
| asInvoker 清单版本（不提权） | 仍然不出 | 排除 manifest |
| 极简 60 行 WinForms 托盘程序 | 计划任务下拉起同样不出，手动就出 | **与 WujieFan 代码无关** |
| `Shell_NotifyIconGetRect` | 手动 = `FOUND (2397,1728)`；任务 = `NOTFOUND hr=0x80004005` | 图标确实没进 shell |
| `Shell_NotifyIcon(NIM_ADD)` 返回码 | 任务下 `ok=False err=5`（`ERROR_ACCESS_DENIED`） | **决定性：添加图标被拒** |
| 同进程另建一个对照托盘（`SystemIcons.Application`） | 任务下同样被拒 | 不是图标资源问题，是整个进程被拒 |
| 定时 `Visible=false; Visible=true` 重注册 5 次 | 5 次全 `NOTFOUND` | 不是启动时序竞态，是永久性拒绝 |
| `QueryInformationJobObject(NULL, JobObjectBasicUIRestrictions)` | 手动与任务都是 `flags=0x0` | 拿到的是最内层 job，带限制的是祖先层，查不到 |

**根因**：进程计划程序把任务的进程放进一个带 UI 限制的 job 对象，该进程及其**所有子进程**都无法向 shell 通知区域注册图标。这不是 UAC 级别问题，也不是代码缺陷；用户环境里无法通过改任务设置绕开。

**修复：两跳启动**（0.2.0 的核心改动）

> 计划任务（**LeastPrivilege**，普通权限）→ `WujieFanLauncher.exe`（`asInvoker`）→ `ShellExecuteEx("runas")` → 经 AppInfo 真正提权 → `WujieFan.exe`（管理员）

关键点：**任务本身必须以普通权限运行**。如果任务已经是 `Highest`，父进程已提权，再调 `runas` 会被 UAC 判定为「同级别」，退化成普通 `CreateProcess`，子进程照样继承那个受限 job（实测失败）。只有父进程是普通权限时，`runas` 才真正经过 AppInfo 服务，由它创建**不在原 job 里**的新进程（实测成功）。

**实测证据**（全链路走产品代码，验证脚本已随临时目录清理，结论记录于此）：
- `Enable()` → `IsEnabled=True`、`IsUpToDate=True`、`Command = E:\WORKS\RTSS-0\dist\app\WujieFanLauncher.exe`
- `Start-ScheduledTask WujieFan` → 12 秒后 `WujieFan pid=2888`
- `Shell_NotifyIconGetRect` → `hwnd=0x3006EC id=1 -> FOUND 2397,1728`
- 通知区域截图里能看到绿色风扇图标（截图未入库）
- `read-aida.py` → `Fan1 3262 / Fan2 2859 / 47°C` 正常

**代价**：每次登录会弹一次 UAC 确认框（`ConsentPromptBehaviorAdmin=0` 时是直接提权无提示，用户机器上会弹）。UI 里已注明「会弹一次 UAC 确认」。

**发布包结构因此改变**：两个 exe 必须放在同一目录。`tools\make-release.ps1` 会分别 publish 主程序与启动器，便携包也要求自带运行时版本的启动器。0.5.1 起两个 exe 各自单文件发布，程序条目只剩这两个 exe 加一份完整性清单，包内容见 §14C。

### 9A.13 风扇两档控制：自动 / 强冷（0.3.0 新增）

**为什么只有两档，而且是「只升不降」**

这是安全决定，不是功能偷懒。EC 的手动 PWM 模式（标志 `0xDC`）有一个已实测的硬特性：**进程被强杀时 EC 不会自动回退**，标志会一直停在 `0xDC`。如果允许用户把转速调到比自动模式更低，那么一旦程序崩溃或被杀，机器就会停在一个「比固件认为安全更低」的转速上持续运行，这是真正会烧机器的场景。

只允许往上走，最坏情况就变成「卡在满转」——吵、费电，但散热永远比固件原本的安排更激进。风险方向从「过热」翻转成「噪音」，这是可接受的取舍。

**两种模式与寄存器语义**

| 模式 | 写什么 | EC 行为 |
|---|---|---|
| 自动（默认） | 只写 `ModeFlag1=0x021F`、`ModeFlag2=0x029F` 为 `0x00` | EC 按自己的温度曲线分档调速，与我们无关 |
| 强冷 | 先写 `ManualPwm1=0x021E`、`ManualPwm2=0x029E` 为 `184`，**再**写两个 `ModeFlag` 为 `0xDC` | 忽略温度曲线，按手动 PWM 定速 |

**写入顺序不能反**。`0x021E`/`0x029E` 是「手动模式下的 PWM 值」，切换瞬间 EC 会立刻采用该寄存器的当前内容。如果先置 `0xDC` 再写 184，中间会有一刻沿用上次遗留的值（可能是 45 之类的低速）；先写值再置标志则始终安全。代码里 `FanReader.SetMode` 严格遵守这一次序，`RPM 值残留`已实测无害：自动模式下 EC 根本不读这两个寄存器。

`184` 是硬件上限（`EcRegisters.PwmMax`）。超过 184 不是「更快」，而是**直接停转**——`200/220/240/255` 实测全部 `RPM=0`。这是本机型最容易踩的坑，写入前一律钳位。

**代码落点**

| 文件 | 内容 |
|---|---|
| `src/WujieFan.Core/Ec/FanMode.cs` | `enum FanMode { Auto, StrongCool }`；`enum FanModeState { Auto, StrongCool, Mixed, Unknown }`；`FanModeResult` |
| `src/WujieFan.Core/Ec/EcRegisters.cs` | 新增 `ManualPwm1/2`、`ModeFlag1/2`、`EmergencyTemperatureC=92`、`EmergencyHoldSamples=3`（后两者现已降为「出厂默认值」，实际生效值来自设置，见 §14B） |
| `src/WujieFan.Core/Ec/FanReader.cs` | `ReadModeState()`、`SetMode(FanMode)`、`Describe(FanModeState)`；`Read()` 顺带回读模式填进 `FanSample.Mode` |
| `src/WujieFan.Core/Config/AppSettings.cs` | 持久化字段 `FanMode`（默认 `Auto`） |
| `src/WujieFan/Ui/MainForm.cs` | 勾选框、状态标签、五个安全路径（见下） |

`FanModeState.Mixed` 是为「两个风扇标志不一致」以及「标志是 `0xA5`/`0xCC` 等不认识的值」准备的。这种情况下界面显示「实际: 异常标志」，不假装自己在某个已知模式里。

**五条安全路径**

1. **启动归一化**（`NormalizeFanModeOnStartup`，`OnFormLoad` 里 `OpenReader()` 之后调用）
   规则：开机后的状态由 `settings.json` 决定，而不是由「上次进程死得干不干净」决定。
   - 设置=自动：若 EC 还停在上次的 `0xDC`（强杀/蓝屏/手动杀的残留），写回 `0x00`；
   - 设置=强冷：重新写一遍满转；
   - 已经一致就不写 EC —— 少一次写入少一次出错机会。

2. **退出恢复**（`ExitApplication` → `EmergencyRestoreAuto("程序退出")`）
   只有当前确实是 `StrongCool` 才动手，避免无谓写入。失败不阻止退出：卡在满转只是吵，不让用户退出才是真问题。

3. **关机/注销恢复**（`SystemEvents.SessionEnding`）
   这是最后一个能写 EC 的时机。**「重启」不是冷启动**——软复位不清 EC 的 RAM，手动标志会原样保留；只有真正断电再开机才复位（已实测确认）。所以注销时主动交还，让重启后的表现也可预期。

4. **过热看门狗**（`CheckThermalWatchdog`，每秒随 `OnTick` 执行）
   条件：当前是强冷 **且** 温度 `>= 92°C` **连续 3 次**（默认值；温度阈值与连续次数均可在设置界面里改，见 §14B）。达到即交还自动并弹框说明。
   要求连续多次是为了不被编译、游戏加载这类瞬时尖峰误触发。触发后置 `_emergencyRestored` 防止每 3 秒反复弹框。

5. **托盘逃生口**（托盘右键「恢复自动风扇」）
   比正常路径更难失败：不看设置、不做「设备已关闭就放弃」的短路，即使设备打不开也照样把设置改成 `Auto`，下次启动会再归一化一次。

**界面与实测**

窗口高度 300 → 340，新增一行「强冷模式 (两个风扇满转)」勾选框，右侧显示由 EC 回读的真实状态（「实际: 自动 / 强冷 / 异常标志」）。勾选框状态每秒按 `sample.Mode` 校准，所以别的程序（比如实验工具）把标志改掉时界面会立刻反映，而不是停在一个不存在的状态上。切换失败时勾选框强制回滚——界面显示「强冷中」而 EC 其实还在自动，是这套功能里最危险的假象。

- **正解**：脚本用 `Start-Process -Verb RunAs` 提权 → `ShowWindow(h, 9)` + `BringWindowToTop` + `SetForegroundWindow` → 校验 `GetForegroundWindow() == h` → `CopyFromScreen`。非提权脚本拿不到提权进程的窗口（UIPI）。
- 找窗口不要用 `Process.MainWindowHandle`：该进程有 8 个窗口。用 `EnumWindows` + `GetWindowThreadProcessId` + 类名以 `WindowsForms` 开头 + 标题非空。
- `DarkDialogForm` 没有标题，`EnumWindows` 按标题找不到 → 直接全屏 `CopyFromScreen` 再裁。

| 2 中：方案 1 + 独立守护进程 | 以上 + **运行中被强杀** | 1 个无界面进程 | 1~2 天 |
| 3 重：服务化 | 以上 + 注销 / 多用户 / 守护永不退 | Windows 服务 | 大 |
| 4 极轻：限时租约 | 忘记复位 | 无 | 极小 |

方案 2 的关键设计（将来要做时照此实现，别再重新设计）：

- **设置文件是唯一真相**，启动时按 `settings.json` 的 `FanMode` 归一化，而不是「启动一律复位」。
  `auto` → 若标志是 `0xDC` 就写 `0x00`；`strongcool` → 先写 PWM 184 再置 `0xDC`（顺序不能反，见坑 48）。

  返回 `WAIT_OBJECT_0` / `WAIT_ABANDONED` 即主程序已死（内核在进程终止时自动释放，`taskkill` 也释放），
  此时读标志若是 `0xDC` 就写 `0x00`；守护自身不退出，继续等主程序重新接管。
- 守护形态：计划任务、登录触发、`RunLevel=HighestAvailable`、**无界面**（不需要托盘，因此不受 job UI 限制那条坑约束）。

## 13. 踩过的坑（教训速查）

1. **RTSS 插件必须用 `__cdecl` 导出**。用 WINAPI(__stdcall) 写带参 `Setup(HWND)` 会双重清栈 → 0xc0000005 @ RTSS.exe+0x105c4。（早期误判成"必须 MFC"，是错的。）
2. **Setup(NULL) 必须返回 TRUE**，那只是能力探测，不是真的给你窗口。
3. **大于 184 的 PWM 会让风扇停转**，不是转速拉满。
4. **PawnIO 必须管理员**；网上说"非管理员可用"指的是"免自签/免关 HVCI"，不是"低权限可跑"。
5. **必须用 LpcIO.bin**；LpcACPIEC.bin 只放行 0x62/0x66，不适用。
6. **端口基址必须是 0x4E**；0x2E 读出垃圾值（应加温度 1..100 合法性校验）。
7. **web_fetch 抓 github / raw.githubusercontent 会被 SSRF 拦截** → 改用 PowerShell Invoke-WebRequest。
8. **PowerShell 里 mkdir ... 2>nul 会生成名为 nul 的 0 字节文件**；建目录一律用 New-Item -ItemType Directory -Path ... -Force。
9. **powershell -Command 里变量会被外层吃掉** → 一律 -File script.ps1。
10. **batch 里 cl 的 /Fe: 与 /Fo: 混写会报 D8003** → 先 cd /d 到输出目录，再用 /link /OUT:。
11. **.ovl 是 GBK 编码**，通用 read 工具读不了。
12. **杀不掉的进程多半是提权进程** → 用 Start-Process -Verb RunAs 提权后再 Stop-Process。
13. **进程死后 OSD 槽文字不自动清** → 需手动清零（早期用 z2.ps1，该脚本已随 `_survey\` 清理删除）。
14. **改完 .ovl 必须重启 RTSS**，源码里没有热重载实现。
15. **.ovl 的 Sources/Layers 计数必须与实际块数一致**，编号必须连续；有空洞或计数不符会让槽位静默变空。
16. **写 .ovl 要用 latin-1 读写**（1:1 字节映射），用 UTF-8 会把原有 GBK 中文图层名改成乱码。
17. **`dist\` 里的 exe 在运行时无法被 publish 覆盖** → 发布前先停进程。判断是否真的更新了要看 mtime 或 dll 里的字符串，publish 在文件被占用时会**静默跳过**、照样打印成功。
18. **不能在 `FormClosing` 里直接改 `ShowInTaskbar`** —— 会重建窗口句柄，使 `e.Cancel = true` 失效，进程被真的杀掉。必须 `BeginInvoke` 延后到关闭流程之后。
19. **`PostMessage(hwnd, WM_CLOSE)` 在 WinForms 里被判定成 `CloseReason.TaskManagerClosing`**，不是 `UserClosing`。要模拟点 × 必须发 `WM_SYSCOMMAND (0x0112) / SC_CLOSE (0xF060)`。
20. **非提权进程无法给提权进程发窗口消息**（UIPI），给提权进程发窗口消息的测试脚本本身也得提权跑。
21. **`PostMessage(HWND_BROADCAST)` 在两个提权进程之间收不到** —— 看起来 `ok=True`，实际没有投递。跨进程唤醒改用命名事件 `EventWaitHandle`。
22. **`.ovl` 的 `PositionX` 不是绝对像素**：负值向右、数值过大图层会静默消失（-120 不可见，-16 正常）。
23. **取窗口截图时 `PrintWindow` 对分层渲染窗口返回 false**，而且配置对话框会挡住渲染区。可靠做法是先把自家窗口收进托盘、再 `CopyFromScreen` 全屏后裁剪，并在真机上肉眼复核一次。
24. **`git push` 被上游重置时 `git fetch` 可能仍然正常** —— 卡的是 git-receive-pack 方向。可用 `gh api` 走 Git Data API 推提交（blob → tree → commit → ref）。
25. **`git ls-tree -r` 会给非 ASCII 路径加引号并转成八进制转义** —— 直接解析会造出名字带引号的重复文件。必须用 `git ls-tree -r -z` 按 NUL 切分并逐字节解码。
26. **不要用 latin-1 读写 UTF-8 的 Markdown 文件** —— 中文锚点全部匹配失败，还会把文件写坏（用 `git checkout --` 还原）。.ovl 才需要 latin-1。
27. **GitHub commit API 返回的日期是 UTC（`Z`）**，本地提交时区是 `+0800`；重建 commit 对象时若直接按 UTC 拼，SHA 必然对不上。另外本地 message 末尾有换行、API 存的是不带的。两点都按好才能复现同一个 SHA。
28. **用 Git Data API 推 commit 前，新 blob 必须先上传**：`POST /git/trees` 只复用远端已存在的 blob，引用了新 SHA 会报 `<sha> is not a valid blob (HTTP 422)`。
29. **`dotnet build` 之后 bin/obj 会重新长出来**（本次 2.62MB），整理目录要在构建验证之后再删一遍；`dist/` 里的 exe 运行时无法被 publish 覆盖（MSB3027），发布前先停进程。
30. **`dotnet publish -p:PublishSingleFile=true` 少了 `IncludeNativeLibrariesForSelfExtract=true`**，自包含单文件仍会在 `%TEMP%\.net\` 里散落原生库，而且部分机器上会启动失败；带上它才是真正的单文件解压即用。
31. **`Stop-Process` 打不掉提权的 WujieFan**（`拒绝访问`）。打包脚本必须提权跑，或者在托盘里手动退出；不要用 `-ErrorAction SilentlyContinue` 把失败吞掉，否则 publish 会静默产出旧文件（MSB3027）。
32. **GitHub Release 资产的 zip 要重新打包时记得带 `--clobber`**，否则 `gh release upload` 报已存在；第一次上传时 zip 里的 README 是打包前的旧版，重新 publish + 重打包 + `--clobber` 才是对的。
33. **`schtasks /Query /XML` 的控制台输出编码在同一台机器上会变**（UTF-8 与 GBK 之间）。固定按任一编码解码都会在中文路径上失败 —— 必须按**原始字节**读，先试严格 UTF-8 再退回 `Encoding.GetEncoding(0)`（系统 ANSI 代码页，需先 `Encoding.RegisterProvider(CodePagesEncodingProvider.Instance)`）。
34. **`schtasks /Query /XML` 会省略「等于默认值」的节点**。`PT72H` 是 v1.2 的默认执行时限，所以读不到 `<ExecutionTimeLimit>` 恰恰意味着「默认 72 小时」，不是「没有限制」。判断缺省项前先查 schema 默认值，别把「没写出来」当成「没有」。
35. **`schtasks /Create ... /XML` 的 XML 必须用带 BOM 的 UTF-16 写入**（`File.WriteAllText(path, xml, Encoding.Unicode)`）。写 UTF-8 会导致中文路径乱码甚至导入失败。
36. **任务 1.2 schema 不接受 `DisallowStartOnRemoteAppSession` / `UseUnifiedSchedulingEngine` 节点**，`/Create /XML` 会报 `任务 XML 包含不应存在的节点`。
37. **`schtasks /SC ONLOGON` 模板会自带 `DisallowStartIfOnBatteries=true` 与 `ExecutionTimeLimit=PT72H`** —— 笔记本拔电源不启动、跑满 72 小时被强杀。要可控就必须自己写完整 XML，不能用 `/SC` 模板。
38. **`dotnet publish` 在目标 exe 运行时静默跳过拷贝**（打印成功但文件没更新）。判断是否真的更新要看 mtime 或 dll 里的字符串。
39. **PowerShell 的 `*>` 重定向写出的日志是 UTF-16LE**，node 里要 `buf.toString("utf16le")` 解，否则全是乱码。
40. **提权 `Start-Process -Verb RunAs` 不能与 `-RedirectStandardOutput` 同用**（报「无法使用指定的命名参数解析参数集」）。正解是写一个内层脚本自己重定向到文件，外层只负责拉起并轮询日志。
41. **提权脚本静默失败（不生成日志）时不要猜**，改用非提权只读查询去验证同一事实（例如查系统自带任务的 XML）。
42. **`RunLevel` 同样会被省略**：任务以 `LeastPrivilege`（默认值）运行时，`schtasks /Query /XML` 的 `<Principal>` 里**没有 `<RunLevel>` 节点**；只有 `HighestAvailable` 才写出该节点（实测：用 `New-ScheduledTaskPrincipal -RunLevel Limited` 注册后 `/Query /XML` 无该节点，`-RunLevel Highest` 则有）。所以「判断任务是不是普通权限」必须写成「节点缺失 或 等于 `LeastPrivilege`」，与第 34 条同一类陷阱。
43. **计划任务拉起的进程无法注册托盘图标**，且子进程继承该限制。表现是 `Shell_NotifyIcon(NIM_ADD)` 返回 `ok=False err=5`（`ERROR_ACCESS_DENIED`）、`Shell_NotifyIconGetRect` 返回 `0x80004005`，而进程本身跑得好好的。这与 UAC 级别无关（Highest 与 Limited 一样失败），也与代码无关（60 行极简托盘程序同样失败）。绕法是**两跳启动**：任务以普通权限跑一个 `asInvoker` 启动器，由启动器 `ShellExecuteEx("runas")` 让 AppInfo 创建新进程。注意**任务不能设成 Highest** —— 父进程已提权时 `runas` 会退化成普通 `CreateProcess`，子进程照样继承受限 job。
44. **判断「是不是真的提权了」不能只看任务设置**，要看进程实际完整性级别与 `NIM_ADD` 的返回码；本次排查里「任务设成 Limited 应该没问题」的直觉错得很远。
45. **极简复现程序是排除法的最强武器**。托盘问题卡了两轮，最后靠一个 60 行、只建一个 `SystemIcons.Application` 托盘的 WinForms 程序在 4 种启动方式下对比（任务 Highest / 任务 Limited / 手动提权）才把「我们的代码有问题」彻底排除。
46. **EC 手动 PWM 模式被强杀后不会自动回退**。`taskkill /F` 掉控制进程后，标志仍是 `0xDC`、PWM 仍是你写的值，转速照旧。任何写 EC 的功能都必须自带「下次启动归一化」，不能只依赖进程内 `finally`。
47. **「重启」不清 EC 的 RAM，只有真正断电才复位**。软重启（warm reset）后手动标志与 PWM 值原样保留；关机再开机（冷启动、掉电）才回到 `0x00`。所以「重启后就没事了」是错的假设。
48. **写手动 PWM 必须先写值、再置标志**。`0x021E`/`0x029E` 是「手动模式下的 PWM 值」，置 `0xDC` 的瞬间 EC 立刻采用它的当前内容；顺序反了会有一刻沿用上次遗留的旧值（可能是 45 这样的低速）。
49. **PWM 超过 184 不是更快，而是停转**。`200/220/240/255` 实测全部 `RPM=0`，184 才是 100% 占空比（约 5700 RPM 物理上限）。所有写入路径都要钳位，界面上也不要暴露 >184 的输入。
50. **判断「界面显示的档位」必须回读 EC，不能信自己的变量**。用户可能在别处改了标志，或上次写入其实没生效。`OnTick` 每秒用 `sample.Mode` 校准勾选框，切换失败时强制回滚 —— 界面显示「强冷中」而 EC 还在自动，是这类功能最危险的假象。
51. **WinForms 勾选框文字是 `AutoSize` 的，右侧再放一个 `AutoSize` 标签会重叠**。把右侧标签设 `AutoSize=false` + 固定宽度 + `TextAlign=MiddleRight` 才稳（实测截图对比过）。
52. **自绘无边框窗口截不出来**：`PrintWindow` 返回 False（空白图），`WM_PRINT(0x0317)` + PRF_* 只得到纯背景色。只能先把窗口提到前台再 `CopyFromScreen`，而且**脚本本身必须提权跑**（非提权脚本拿不到提权进程的窗口，UIPI 会静默给出别人的画面）。
53. **找自己的窗口不要用 `Process.MainWindowHandle`**：WinForms 程序有 8 个窗口（1 个可见主窗 + 7 个不可见辅助窗），`MainWindowHandle` 可能命中错的那个。用 `EnumWindows` + `GetWindowThreadProcessId` + 类名以 `WindowsForms` 开头 + 标题非空。
54. **自绘文本的矩形必须在布局阶段一次算好存成字段**。`DarkDialog` 里 `LayoutDialog()` 与 `OnPaint()` 各推一套坐标，差一个间距就表现为「正文压到标题上」+「第二行被裁掉」。
55. **托盘菜单项的 `ForeColor` 会被统一染色循环覆盖**。给某一项单独设色（如「退出」用红色）后，末尾那个 `foreach (item) item.ForeColor = ...` 必须跳过它，否则看不到效果。
56. **`TextFieldParser`/`Dpi.Px(Control, float)` 这类帮助方法只接受 `Control`**，`ToolStripItem` 不是 `Control`，在菜单项里算 DPI 会编译不过，直接用字面量内缩。

## 14. 本轮审计（2026-11）来源与结论

2026-11 对本仓库做过一轮只读审计，按领域分成五份，全程未改动代码：EC / 风扇安全（t1）、
Windows 权限与提权链（t2）、C# 架构（t3）、测试覆盖（t4）、发布与文档一致性（t5）。
据此产出 `docs\02-路线规划与优先级.md`，它只做取舍与排序、不重复取证，视为**规划存档**并保持原样；
五份审计的全文与取证记录留在 AgentTeams 的任务记录里，**不在本仓库内**。

审计结论落地为一批修复：EC 层硬化、看门狗重写、配置原子写、启动器完整性清单、版本号单一来源、文档数字对齐。
下文列的是审计时点最严重的三条 P0，**均已在同批修复中处理**。

1. **PWM 夹取层**（t1-P0-1）：新增 `EcAccess.WritePwm`，越界直接抛 `EcException` 而**不是静默夹取**——
   静默夹取会把调用方的 bug 藏起来。`EcRegisters` 补 `PwmMin = 0` 与四个模式常量，
   模式标志不再散落字面量。
2. **读失败跳过看门狗**（t1-P0-2）：读失败路径现在也走看门狗（`CheckWatchdogOnReadError`），
   判据从「EC 回读是不是强冷」改为「本次会话是否仍持有强冷意图」——原判据恰好否定了它要防的场景
   （别的软件把标志改回自动后我们就该交还控制权）。阈值是连续 3 次且持续 ≥2 秒。
3. **SetMode 无回滚**（t1-P0-3）：写入前快照四个寄存器，中途失败先交还自动、再还原快照 PWM；
   回滚也失败时通过 `FanModeResult.Indeterminate` 上抛，界面置未知态并显著提示，而不是只写日志。
   还原快照刻意用原始 `Write` 而非 `WritePwm`——快照值可能是别的软件留下的越界值，用带校验的写会再抛一次异常。

其余同批落地：配置原子写（tmp + `File.Replace`，失败置 `LastError` 并返回 bool）、启动器完整性清单
（`WujieFan.integrity.json`，构建时生成）、启动器参数白名单、版本号收敛到 `Directory.Build.props` 单一来源。

**签名校验没有实现，也不保留默认关闭的分支**：启动器只做 SHA-256 清单比对，定位是「检测而非防御」——
清单与 exe 同在可写目录，能替换 exe 的人同样能替换清单。启用代码签名校验的唯一前提是先有代码签名证书；
在那之前留一个「默认关闭」的开关只会让人误以为这层保护存在。

### 14A. 0.6 结构性改造（同批完成）

审计之后又在同一批里做了结构性改造，均已落地并纳入回归：

| 项 | 结果 |
| --- | --- |
| 单测工程 | `tests\WujieFan.Core.Tests\`（xUnit），**148 个 test case**（84 `[Fact]` + 15 `[Theory]` 的 61 组 `[InlineData]` + 3 条回读路径断言），全绿 |
| 传输层抽象 | `IEcTransport` / `IClock`；`FanReader(IEcTransport, IClock?)` 可注入假传输，写序、回滚、看门狗路径可无硬件断言 |
| MainForm 拆分 | 1618 → **580 行**；分出 `FanModeController`(564) / `FanPollingController`(254) / `TrayHost`(205) / `TitleBarChrome`(204) / `RtssPublisher`(120)，全构造注入，无 DI 容器、无静态单例 |
| CI | `.github\workflows\ci.yml` + `tools\verify.ps1` 统一入口：build / test / 版本一致性 / autostart-test / XML 契约，退出码 0 通过、1 失败、10 跳过 |
| AIDA 撕裂 | **已评估并否决 seqlock**，见下 |

**为什么不做 AIDA 写入 seqlock**：三份证据指向同一结论。其一，`AidaSharedMemory` 的布局不是定宽槽位数组，
而是 GetSystemMetrics 式的 XML 文本片段（`<fan><id/><label/><value/></fan>`，单帧实测 215~217 字节），
没有可以原子切换的「槽位」；其二，seqlock 是**读者配合**协议，而 RTSS 用 `CString s = pMapAddr` 一次性取串，
既不读序号也不重试，序号写了没人看；其三，实测把单次 `Marshal.Copy` 拆成「清首字节→改写正文→写回首字节」
这个看似标准的发布流程，**撕裂从 46 次/40 万读恶化到 8,803 次（191 倍）**，空读率从 2.13% 涨到 13.61%——
拆成多次写反而拉长了窗口。现有单次拷贝 p99 = 3.70 µs，1 Hz 发布 + 60 fps 读取的窗口占比 3.7e-6，
按真实节奏 1,790 万次读 **0 次撕裂**；两组变长/等长压测共约 1.6e7 次读，**从未出现任何从未被写入过的合成数值**。
即最坏情况是读到上一帧或截断串，不会显示一个「看起来合法但错误」的转速。故保留单次拷贝，只加结论注释。

**回归边界**：过热看门狗的两条判据（默认 92℃ 连续 3 次、读失败 3 次且 ≥2 秒；前者已可配置，后者仍是硬编码常量）在 `src\WujieFan\Ui\FanModeController.cs`
里，属 UI 项目、依赖 WinForms，而测试工程只引用 Core，因此**无法在无 UI 环境断言**——这是分层边界，不是遗漏。

**写 EC 的实机链路（2026-11-17 实跑，此前只在本机手工验过）**：三项全通过，退出码均为 0。
`--fanmode-live` 6/6：切换前自动 69°C、Fan1 3152 / Fan2 2796 RPM；强冷 3 秒后 59°C、
Fan1 **5600** / Fan2 **5586** RPM；交还自动 4 秒后 62°C、回落 Fan1 2803 / Fan2 4922 RPM，末行打印 `[恢复] 已交还自动模式`。
重跑一遍数字一致（5600 / 5586、2803 / 4922），封顶值与 `EcRegisters.PwmMax = 184` 换算的约 5700 RPM 物理上限相符。
`--autostart-cn` 通过（`E:\测试\WujieFan.exe` 中文路径往返）；`--autostart-upgrade` 通过（旧定义 `DisallowStartIfOnBatteries=true` +
`PT72H` 被修正为 `false` / `false` / `PT0S`，`RunLevel=LeastPrivilege`、指向 `WujieFanLauncher.exe`，`IsUpToDate` 由 false 转 true）。
测试用的 `WujieFanCnTest` / `WujieFanUpgradeTest` 任务与 `E:\测试` 目录均无残留；事后直读 EC 为 PWM1 46.2% / PWM2 39.7%
（Fan1 3092 / Fan2 2726 RPM），确认已被 EC 自动曲线接管，**没有留下写死的手动 PWM**。
`--autostart-live` **刻意没跑**：它用真实任务名 `WujieFan`，末尾会 `Disable()`，跑完等于把用户的开机自启关掉；
它覆盖的任务 XML 五项与 Round-trip 已由 `--autostart-cn` / `--autostart-upgrade` 在独立任务名下覆盖。

### 14B. 设置界面与可配置过热保护（随 v0.5.0 发布）

**为什么加设置界面**：主面板的定位是「看一眼就走」的仪表板 —— 三张数据卡加一条状态栏，用户扫一眼风扇转速和温度就关。开关一行行往主面板上铺，最先被挤掉的就是数据卡。所以把「开机自动启动」「向 RTSS 提供数据」两个开关收进设置对话框（`src\WujieFan\Ui\SettingsDialog.cs`，531 行），主面板只留「强冷模式」一行和一个「设置」入口；托盘右键菜单同步加了「设置...」。设置对话框不落盘，只把值交回调用方 —— `Save()` 失败该由谁来提示、怎么提示，是调用方的决定，不是弹窗的。

**两个新设置项**（`AppSettings`，默认值取自 `EcRegisters` 常量，常量本身保留作出厂锚点，单测仍用它断言）：

| 项 | 语义 | 默认 | 可设范围 |
| --- | --- | --- | --- |
| `EmergencyTemperatureC` | 过热保护的温度阈值（℃） | 92 | 70–100 |
| `EmergencyHoldSamples` | 需要连续多少次采样达标才动手 | 3 | 1–60 |

**越界回默认，而不是夹到边界**：`Load()` 读到越界值直接还原成出厂默认（`AppSettings.cs:236-247`）。夹到边界看着更「宽容」，但这条链的上界恰恰是危险的：EC 温度寄存器的有效量程是 1..100，把用户填的 `999` 夹成 `100` 等于把保护关掉 —— 永远达不到，看门狗形同不存在。回默认至少保证它还在工作。

**读取侧还有一层兜底**：`FanModeController` 每次判定时现读设置（不是构造时快照，用户中途改了立刻生效），再 `Math.Clamp` 一次（`FanModeController.cs:114-123`）。理由是配置文件是明文、可以手改，而看门狗宁可用一个被修正过的阈值，也不能因为参数荒唐就干脆不工作 —— 这里夹取而非抛异常，与 EC 写入层「越界抛异常、不静默夹取」的取向刚好相反，因为前者防的是用户误操作，后者防的是调用方 bug。

**不改设置 = 行为与 0.4.x 完全一致**：默认值就是原常量值（92 / 3），判定逻辑（连续达标、单次尖峰不触发、触发后置 `_emergencyRestored` 不反复弹框）一条没动，只把常量换了来源。

### 14C. 发布包瘦身：单文件与包内容收敛（随 v0.5.1 发布）

**为什么要瘦**：用户对 0.5.0 发布包的直接反馈是「太琐碎」——一个只做两件事的小工具，依赖框架版解压出 18 个条目，
其中 10 个是程序文件：`WujieFan.exe` 与 `WujieFanLauncher.exe` 各自还跟着 `.dll`、`.deps.json`、`.runtimeconfig.json`，
再加 `WujieFan.Core.dll` 与一份完整性清单。哪几个能删、哪几个删了就起不来，用户无从判断；
另有 5 个 `tools/` 条目需要 Python 才能用。功能没变，是交付形态离「解压即用」的预期太远。

**框架依赖包也能单文件**。`tools\make-release.ps1:76`（主程序）与 `:80`（启动器）都用
`--self-contained false -p:PublishSingleFile=true -p:DebugType=none`。`PublishSingleFile` 折进 exe 的只是**托管**程序集
（含作为嵌入资源的 `LpcIO.bin`）与 `deps.json` / `runtimeconfig.json` 这些启动期元数据；.NET 8 Desktop Runtime 仍从本机取——
这正是 `--self-contained false` 的原义，所以包的体积不会因此膨胀，也不是「伪单文件」。
便携包（`:84`、`:89`）在同一组参数上再加 `-p:IncludeNativeLibrariesForSelfExtract=true`，否则原生库会散落到
`%TEMP%\.net\` 里，部分机器上还会启动失败（见 §13 第 30 条）。

**实测输出**（captain 2026-11-18 的构建数据，本轮未复测）：多文件时主程序的 publish 目录是 5 个文件
（`WujieFan.exe` / `.dll` / `.deps.json` / `.runtimeconfig.json` / `WujieFan.Core.dll`），启动器另有 4 个；
单文件后主程序只剩 **1 个 exe（645,711 B）**，启动器再 publish 到同一目录、加上后补的完整性清单，
最终目录里是 3 个文件。
启动后 `tools/read-aida.py` 读到 `Fan1 3175 / Fan2 2826 / 60°C`，与 0.5.0 的多文件版读数一致——
说明核心库逻辑、嵌入的 PawnIO 模块、向 AIDA 共享内存供数这三条链路在单文件形态下都还在。

**为什么不能只留一个 exe**（这是设计约束，不是打包时偷懒）

`src\WujieFan\app.manifest:13` 是 `requireAdministrator`。用户双击 exe 当然能正常提权运行，问题在**开机自启**这条路径上：
计划任务拉起的进程会被放进一个带 UI 限制的 job 对象，其中的 `Shell_NotifyIcon(NIM_ADD)` 直接返回
`ERROR_ACCESS_DENIED(5)`，托盘图标永远不出现，而且这个限制会被所有子进程继承——任务设成 Highest 还是 Limited 都一样
（逐步排查与实测证据见 §9A.12）。所以任务只能以**普通权限**运行一个 `asInvoker` 的启动器，由它
`ShellExecuteEx("runas")` 经 AppInfo 服务提权拉起主程序：只有 AppInfo 新建的进程才不继承那个受限 job。
这条链路的原始说明写在 `src\WujieFan.Core\Config\AutoStartManager.cs:14-26`。

换句话说：主程序**必须**是 `requireAdministrator`（否则读不到 EC），而能被计划任务可靠拉起的进程**必须**是 `asInvoker`，
两个要求落在同一个可执行文件上会互相打架。**两个 exe 是这两条要求的最小解**，合并成一个就必然放弃开机自启时的托盘图标。

**包内容**（按脚本当前写法，`tools\make-release.ps1:143-194`）：

| 组成 | 框架依赖包 `WujieFan-<版本>-win-x64.zip` | 自包含便携包 `...-portable.zip` |
| --- | --- | --- |
| 程序 | `WujieFan.exe`、`WujieFanLauncher.exe`、`WujieFan.integrity.json` | 同左（主程序与清单取自自包含主程序目录，启动器另取自自包含启动器目录） |
| 文档 | `README.md`、`THIRDPARTY.md`、`LICENSE` | 同左 |
| zip 条目数 | 6（3 程序 + 3 文档） | 6（3 程序 + 3 文档） |
| 0.5.0 对照 | 18 条目（10 程序 + 5 tools + 3 文档） | 11 条目（3 程序 + 5 tools + 3 文档） |

程序条目从 10 个减到 3 个，`tools/` 的 5 个条目整个消失。为防「publish 悄悄退化成多文件」而打出散碎包，脚本改成显式白名单
`$script:AppFileWhitelist`（`:109`），并且缺文件即报错、目录里出现白名单以外的非 `.pdb` 文件也即报错（`:149-163`）——
打空包、打残包会在打包阶段失败，而不是等用户解压后才发现。

完整性清单（`New-IntegrityManifest`，`:123-142`）只收录**磁盘上真实存在**的文件：便携包的主程序是单文件，
`WujieFan.Core.dll` 已经并进 exe，硬把它写进清单会让每个便携包用户每次开机都看到一条误报。
启动器侧对「磁盘上没有、清单里也没有」的组件直接跳过、不计为问题（`src\WujieFan.Launcher\Program.cs:299-304`），两端口径一致。
清单的定位仍是**检测而非防御**——它与 exe 同处一个可写目录，能替换 exe 的人也能一起替换清单，真正的修复是代码签名或受保护安装目录。

**tools/ 不再随包分发**：`verify.ps1`、`make-release.ps1` 是开发与发布工具，`add-wujie-layers.py`、`read-aida.py` 等还需要本机有 Python，
普通用户拿到也用不上，只是「这堆东西是什么、能不能删」的噪音来源。脚本的 `Add-Docs`（`:97-103`）只加三份文档，
注释里写明「仓库里 tools/ 保留不动, 只是不分发」——能力没有删，只是不再塞进用户手里。
