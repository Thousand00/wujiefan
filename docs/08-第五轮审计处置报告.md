## 1. D2：`ModeSnapshot` 只存两个从不下读的字段 —— 已改

### 问题

`src/Zephyr.Core/Ec/FanReader.cs:466`（改前）：

```csharp
/// <summary>写入前四个寄存器 (两个手动 PWM、两个模式标志) 的取值。</summary>
private readonly record struct ModeSnapshot(int Pwm1, int Pwm2, int Flag1, int Flag2)
{
    public static ModeSnapshot Capture(IEcTransport ec) => new(
        ec.Read(EcRegisters.ManualPwm1),
        ec.Read(EcRegisters.ManualPwm2),
        ec.Read(EcRegisters.ModeFlag1),
        ec.Read(EcRegisters.ModeFlag2));
}
```

`Capture` 在 `SetMode` 里被调一次（`:289`，写事务 `try` 之前）。它的用途只有一个：写到一半失败时让 `RecoverToAuto` 把 EC 还原。

而 `RecoverToAuto`（`:410`）只用了两个 PWM：

```csharp
TryWrite(EcRegisters.ModeFlag1, EcRegisters.ModeAuto, problems);
TryWrite(EcRegisters.ModeFlag2, EcRegisters.ModeAuto, problems);
TryWritePwm(EcRegisters.ManualPwm1, snapshot.Pwm1, problems);
TryWritePwm(EcRegisters.ManualPwm2, snapshot.Pwm2, problems);
```

两个模式标志用的是常量 `EcRegisters.ModeAuto` —— **回滚的目标固定是自动模式，读回来的旧标志没有用处**。所以 `Flag1` / `Flag2` 是存了从不读的字段，而读它们的两次 I2C 是每次切模式都白跑。

### 改法

```csharp
/// <summary>
/// 写入前两个手动 PWM 寄存器的取值。
///
/// 这里只存值得还原的东西。两个模式标志不用存: 回滚一律写成
/// <see cref="EcRegisters.ModeAuto"/> 常量 (见 <see cref="RecoverToAuto"/>) ——
/// 目标固定是自动, 读回来的旧标志没有用处。早先的快照也读了标志,
/// 等于每次切模式多跑两次 I2C, 却一次都没用过。
/// </summary>
private readonly record struct ModeSnapshot(int Pwm1, int Pwm2)
{
    public static ModeSnapshot Capture(IEcTransport ec) => new(
        ec.Read(EcRegisters.ManualPwm1),
        ec.Read(EcRegisters.ManualPwm2));
}
```

调用点（`:289`）与 `RecoverToAuto` 的签名都不用改 —— 它们只用 `Pwm1` / `Pwm2`。

### 测试同步

`tests/Zephyr.Core.Tests/FanModeWriteSequenceTests.cs` 里那条测试原来叫「写入前先抓四个寄存器的快照」，名字现在是错的，改为「写入前先抓手动PWM的快照」。

更重要的是加了一条断言，防止以后有人又把标志读回来：

```csharp
// 回滚一律把标志写成常量 ModeAuto, 所以快照不需要读标志。
// 那两次读不但没用, 还是每次切模式白白多出的 I2C 往返。
```

原来那条「快照必须在第一次写入之前」的时序断言保留不变（它只认 `ManualPwm1` / `ManualPwm2`，不受本次改动影响）。

## 2. D1：`HasData` 不是死代码 —— 驳回

报告原文：

> `FanSample.cs:57` 的 `public bool HasData => Error is null && Fans.Count > 0;` 在 src/ 内 grep 零引用，tests/ 也零引用。完全孤儿属性。一轮审计就报过，到现在还没删。

「src/ 零引用」是对的 —— 生产代码确实不用它。但「tests/ 也零引用」不成立，`tests/Zephyr.Core.Tests/FanReaderSamplingTests.cs` 里有 3 处：

| 行 | 断言 |
| --- | --- |
| 30 | `Assert.True(s.HasData)` |
| 52 | `Assert.True(s.HasData);   // 温度无效不影响风扇读数` |
| 119 | `Assert.False(s.HasData)` |

删掉这个属性，这 3 条测试会编译失败。

这条也不该按「孤儿」处理。它是 `FanSample` 上一个明确的语义出口 —— 「这次采样到底有没有有效数据」。测试正是靠它把「读到 0 转速」「温度无效」「读取失败」这几种情形分开断言的。没有它，测试只能退回去比较 `Error is null && Fans.Count > 0` 这个表达式本身，等于把实现抄进测试。

如果确实想减少公开面，可选的做法是把它标成只在测试里可见（`[assembly: InternalsVisibleTo]`），但那要动可见性语义，收益不抵风险。这一条**不改**。

## 4. 报告正文里的两处事实错误

这两条不是「建议照做」的条目，是报告描述现有实现时说错了。记下来是因为它们会影响后续审计的判断基准。

### 4.1 「`AppSettings.Load()` 有 `Interlocked.Exchange(ref _loadLockTaken, 1)` 做跨进程互斥」

全仓 grep `_loadLockTaken` 与 `loadLock` **零命中**。`AppSettings.cs` 里对 `Interlocked` / `lock` / `Mutex` 的搜索只命中一处 —— `:171 public static AppSettings Load()` 本身，也就是说 `Load()` 里既没有锁也没有 Interlocked。

`Load()` 的实际结构（`:171-194`）：

```csharp
public static AppSettings Load()
{
    LoadDegraded = false;
    LoadNormalized = false;
    LoadWarning = null;
    LoadMigrated = false;
    LoadMigrateError = null;
    LastError = null;

    // 改名后第一次启动: 新目录还没有配置文件, 但旧目录有, 就沿用过来。
    TryMigrateFromLegacyDirectory();

    string json;
    try
    {
        if (!File.Exists(FilePath)) return SafeDefaults();
        json = File.ReadAllText(FilePath);
    }
    catch (Exception ex)
    {
        LastError = ex.Message;
        return Degrade("读取设置失败, 已按安全默认启动 (不接管风扇): " + ex.Message);
    }
    ...
}
```

即使真有那个字段也不成立：`Interlocked` 是**进程内**原语，做不到跨进程互斥。要跨进程得用命名 `Mutex`。目前的多实例并发靠的是「后到者 `File.Copy(overwrite: false)` 失败 → 捕获 → 检查文件是否已在位」这条路径（v0.6.2 加的），不是锁。

### 4.2 「`QueryState` 四态（NotInstalled / Inconclusive / Installed / Foreign）」

实际（`src/Zephyr.Core/Config/AutoStartManager.cs:71-77`）：

```csharp
public enum TaskState
{
    /// <summary>没查成 (schtasks 超时/起不来)。任何结论都不能基于这个状态。</summary>
    Unknown,
    /// <summary>确实没有这个任务。</summary>
    Absent,
    /// <summary>任务存在且属于本程序。</summary>
    Ours,
    ...
}
```

四个名字全对不上。这里不只是命名差异 —— 报告把 `Unknown`（查询失败、结论不可用）和 `Absent`（确认不存在）的区分漏掉了。这个区分是 v0.5.6 那次修复的核心：早期版本把 `Unknown` 当成 `Absent`，于是 schtasks 超时会被报成「已关闭（本来就没有自启动项）」。
