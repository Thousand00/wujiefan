## 1. N1 — 供数可能永久停掉（真缺陷，已修）

### 报告说的现象

`RtssPublisher.PublishUnavailable` 不重建共享内存。

### 实际链条，比报告描述的更糟

`RtssPublisher` 有两条发布路径：成功采样走 `Publish`，读失败走 `PublishUnavailable`。而重建 AIDA 共享映射的代码**只挂在 `Publish` 里**：

```csharp
// 原 Publish
if (_aida is not { IsOpen: true } && DateTime.UtcNow.Ticks - _lastTryTicks >= RetryIntervalTicks)
{
    _lastTryTicks = DateTime.UtcNow.Ticks;
    Apply();
}

// 原 PublishUnavailable —— 第一句就返回
if (_aida is not { IsOpen: true } || _lastFanEntries is null) return;
```

于是：

1. 某次成功采样时 `Publish` 写到一半抛异常 → `catch` 里 `aida.Dispose(); _aida = null;`，映射被丢掉；
2. 此时 EC 也读不到（休眠恢复失败、被 HWiNFO 之类占锁）→ 轮询走**失败分支**，`Publish` 根本不会被调用；
3. `PublishUnavailable` 看到 `_aida` 为 null 直接返回，**也不重建**。

结果：既没有数据，也没有任何一条路径能把映射建回来，直到某次采样碰巧成功。而"EC 本来就不正常"正是最需要覆盖层显示无数据的时候。

### 修法

把重建抽成单一入口，两条发布路径都先过它：

```csharp
private AidaSharedMemory? EnsureOpen()
{
    if (_aida is { IsOpen: true }) return _aida;
    if (DateTime.UtcNow.Ticks - _lastTryTicks >= RetryIntervalTicks)
    {
        _lastTryTicks = DateTime.UtcNow.Ticks;
        Apply();
    }
    return _aida is { IsOpen: true } ? _aida : null;
}
```

`Apply()` 的 10 秒退避保持不变，不会每秒重试刷状态栏。

**返回实例而不是 bool** 是刻意的：调用方拿到非空引用后编译器能做流分析。改成 `bool TryEnsureOpen()` 会产生 4 个 `CS8602: 解引用可能出现空引用`。

### 验证

UI 层的 `RtssPublisher` 是 `internal` 且依赖 `AppSettings`，单测够不到，改用反射探针：

- 置 `_aida = null`、`_lastTryTicks = 0`、`_lastFanEntries = null`（模拟"映射被丢 + 退避已过 + 尚未成功发布过"）；
- 反射调 `PublishUnavailable()`；
- 结果：`_aida is null = False ; IsOpen = True` → **PASS**。

**变异验证**：把 `PublishUnavailable` 改回旧写法，同一探针立刻报 `_aida is null = True ; IsOpen = False` → **FAIL**；恢复后 PASS。双向成立。

## 2. N2 — 退出时对 EC 写了两次自动（真缺陷，已修）

### 报告说的现象

`_shutdownRestoreStarted` 只加在 `RestoreAutoOnShutdown()`，`ExitApplication → RestoreAuto("程序退出")` 绕过它。

### 一处更正

报告写"第一次没被拦、第二次被拦"。实际读代码：`ExitApplication` 走的是 `RestoreAuto`（无标志）→ **写一次**；随后 `Close()` → `Dispose()` → `RestoreAutoOnShutdown()`（有标志，但此刻是第一次进）→ **又写一次**。所以是**两次都写**，标志只在后一处且没能阻止任何一次。

### 修法

新增 `RestoreAutoOnExit()`，与 `RestoreAutoOnShutdown()` 共用同一个 `Interlocked.Exchange` 标志：

```csharp
public void RestoreAutoOnExit()
{
    if (Interlocked.Exchange(ref _shutdownRestoreStarted, 1) != 0)
    {
        UiLog("RestoreAutoOnExit: 已经执行过, 本次跳过");
        return;
    }
    FanReader? reader = _reader();
    if (reader is { IsOpen: true } && reader.ReadModeState() == FanModeState.Auto)
    {
        UiLog("RestoreAutoOnExit: EC 已经是自动模式, 不需要再写");
        return;
    }
    RestoreAuto("程序退出");
}
```

`MainForm.ExitApplication()` 里原来那三行"预读判断 + RestoreAuto"收进这个方法，改成单行调用。这样"退出时会不会写 EC"只有**一个决定点**。

写自动虽然幂等，但不能靠幂等糊过去：两次读改之间只要 EC 被别的软件动过，后一次就会基于中间态做判断、甚至误报"状态不确定"。

改为加一条不变量测试（`HotKeyComboTests.cs`）：

```
加载之后的热键字段必须是可解析的
```

对 `""` / `Ctrl+Shift+End` / `ctrl+alt+f9` / `Ctrl+0x2C` / `Alt+Win+F1` 五种写法，经 `WriteSettings` + `Load()` 后断言：不降级、非空时必须 `TryParse` 成功、且 `ToSettingString()` 幂等。

## 4. N4 — `OnSessionEnding` 缺 `InvokeRequired`（**我否决了报告的修法**）

报告的判定是对的（与 `OnPowerModeChanged` 不对称）。但它建议的修法我**没有照做**。

### 为什么不同意

关机/注销是有**截止时间**的。`BeginInvoke` 只是把工作排进消息队列，Windows 完全可能在它被执行之前就结束进程 —— 那样风扇交还就悄无声息地没做。而"退出时没交还"正是这个程序最不该出的问题：下次开机 EC RAM 不清，风扇会满转。

同步执行至少保证在返回前做完。

### 为什么同步是安全的

该方法做的三件事：交还 EC、改设置、写日志 —— **全都不碰控件**，在哪个线程跑都不会崩。

### 代价，写成明确约束

在方法注释里写死：

> **谁在这里加任何与界面相关的调用，都必须先切回 UI 线程**。
> 这不是隐含假设，是这个方法存在的条件。

只补了一处 `if (_disposedUi || IsDisposed) return;`。

## 5. N5 — `ExitApplication` 的 `ReadModeState()` 无互斥预读（**报告结论不成立**）

报告说 `ExitApplication` 里的 `reader.ReadModeState()` 是无互斥预读。

**实际代码**（`src/WujieFan.Core/Ec/FanReader.cs`）：

```csharp
public FanModeState ReadModeState()
{
    if (_mutex is not null && !_mutex.Acquire(MutexTimeoutMs)) return FanModeState.Unknown;
    try { ... }
    finally { _mutex?.Release(); }
}
```

这一层互斥是上一轮（v0.5.6，审计条目 A5-P1）已经加的，当时加它的理由正是"结果会被拿去决定退出时要不要交还"。报告基于旧版代码。

另外，N2 的修法把这段预读整体收进了 `RestoreAutoOnExit()`，现在连调用点都只有一处。
