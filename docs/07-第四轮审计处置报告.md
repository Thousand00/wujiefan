## 1. R2：旧版进程并存 —— 已修

### 问题

改名之后两个版本的单实例互斥量不同名：

| | 互斥量 |
| --- | --- |
| 旧版 | `Global\WujieFan_SingleInstance` |
| 新版 | `Global\Zephyr_SingleInstance` |

所以「装完新版、旧版忘了关」时，两个进程会**同时活着**，一起去抢 EC 的两把锁（`Global\Access_ISABUS.HTP.Method` / `Global\Access_EC`）。`FanReader.MutexTimeoutMs` 是 300 毫秒，抢不到就进读失败分支 —— 两个版本**都控制不了风扇**，状态栏反复报「EC 正被占用」。

报告说这是「用户体验问题」。我认为比这重一点：用户看到的不是「有个提示」而是「风扇不管用了」，并且**没有明显线索指向"你把旧版留着"这个真正原因**。

### 修法

`AutoStartManager` 新增 `LegacyProcessRunning()`：

```csharp
public static bool LegacyProcessRunning()
{
    try
    {
        return Process.GetProcessesByName(RuntimeIdentity.LegacyProcessName).Length > 0;
    }
    catch
    {
        return false;
    }
}
```

`RuntimeIdentity` 加 `LegacyProcessName = "WujieFan"`（与 `LegacyTaskName` 同属兼容组）。

`MainForm.OnFormLoad` 里检测并置 `_legacyProcessNotice`，在状态提示链末尾覆盖为：

> 检测到旧的 WujieFan 进程还在运行，两个版本会抢 EC 锁导致都控制不了风扇。请先退出旧版。

**为什么不替用户结束进程**：结束别人的进程属于改动用户系统（和「不替用户删计划任务」是同一条原则），而且旧版是提权进程，普通权限本来也杀不掉 —— 写了也是自欺欺人的代码。

**为什么与旧任务提示分开两条**：旧**任务**要等到下次开机才起作用；旧**进程**是现在就在抢锁。两条同时命中时优先显示进程那条。

### 验证

现有夹具造不出「另一个进程叫 WujieFan」，所以用了个笨办法：把 `powershell.exe` 复制成 `WujieFan.exe` 启动（`Start-Sleep 15`），再用反射调 `LegacyProcessRunning()`。

| 状态 | 返回值 |
| --- | --- |
| 基线（无 WujieFan 进程） | `False` |
| 假进程在跑 | `True` |
| 结束后 | `False` |

**中途一次无效探针（记下来）**：第一次我用 `notepad.exe` 复制成假进程，两次都返回 `False`，我差点当成「检测逻辑坏了」。实际是 Win11 的 notepad 是个 Store 存根，`Start-Process` 之后**立刻就退出了**（探针输出 `alive=False`）。换 `powershell.exe` 才得到能驻留的进程。教训：探针返回「没变化」时要先确认探针本身在动。

## 2. 迁移失败的原因被吞掉 —— 报告没提，我自己挖出来的

### 问题

`AppSettings.LastError` 的语义是「最近一次 Load/Save 的失败原因」，它会在**下一次 Save 时被覆盖**。而旧配置迁移失败时，原因只写进了 `LastError` —— 于是出现这种情况：

1. 用户从 WujieFan 升到 Zephyr，新目录无配置 → 触发迁移；
2. 迁移因为权限/磁盘/文件被独占失败，只设了 `LastError`；
3. 用户的快捷键、过热阈值、RTSS 开关**全部回到默认值**，界面上**没有任何提示**；
4. 用户切一次强冷模式 → `Save()` 成功 → `LastError = null`，原因彻底消失。

用户看到的只有「新版本把我的设置弄丢了」。

### 修法

新增一个不会被冲掉的独立信号：

```csharp
public static string? LoadMigrateError { get; private set; }
```

`Load()` 开头清零，迁移 catch 里赋值，界面据此提示：

> 旧版本的设置没能沿用过来，本次按默认设置启动：`<原因>`

### 顺带修掉一处会制造假故障的地方

两个实例同时启动会撞上同一次迁移：双方都通过 `File.Exists(FilePath)` 检查，只有先到的那个 `File.Copy` 成功，后到的抛「文件已存在」（IOException）。

这其实**不是失败** —— 配置就在位（先到者写的），后续读取照常。但原代码会把它记成错误，于是「开机自启 + 手动点快捷方式」这种常见组合每次都会在日志里留一条假故障。现在只在文件确实仍不存在时才记录。

### 测试

单测 252 → **254**，新增互为反面的两条：

- `迁移失败必须留下可观测的痕迹` —— 制造失败的手法是：在新配置位置放一个同名**目录**。`File.Exists` 对目录返回 `false`（于是走到复制那一步），而 `File.Copy` 往目录路径写会抛异常。断言 `LoadMigrateError` 非空、`LoadMigrated` 为 false、设置回到安全默认。
- `迁移成功之后不该留下失败痕迹` —— 确认上一条不是因为 `LoadMigrateError` 永远非空才通过的。

### 一条断言我写错了，改的是断言不是实现

第一版我断言「迁移失败必须 `LoadDegraded == true`」，测试红了。查下来是我错了：迁移失败后 `File.Exists(FilePath)` 为 false，代码走 `return SafeDefaults()`，**不是**降级分支。而这才是正确语义 ——

- **降级** = 文件在那儿但读不出来，所以不敢接管风扇；
- **没有配置** = 全新安装的正常状态，安全默认（自动模式）本身就是安全态。

用户可见性由 `LoadMigrateError` 单独承担。我把断言改成 `Assert.False(AppSettings.LoadDegraded)` 并写清了理由。

### 变异验证

把 `LoadMigrateError = ex.Message;` 删掉 → `迁移失败必须留下可观测的痕迹` 立刻变红（253 通过 / 1 失败）。恢复后 254 全过。

**一个诚实的缺口**：并发保护那一段（`if (File.Exists(FilePath)) return;`）**没有**被单测钉住 —— 单进程造不出「两个实例同时迁移」。我把整段删掉跑了一次，254 条仍然全过。它现在只有代码注释和发布说明作为依据，我不打算假装它被测住了。

## 3. R1：报告结论不成立

报告说：

> 两个实例的 `LoadMigrated` 都被设成 `true`（因为都执行到了 L449 `LoadMigrated = true`）

我核对了 `src/Zephyr.Core/Config/AppSettings.cs` 的实际结构：

```csharp
try
{
    if (File.Exists(FilePath)) return;
    if (!File.Exists(LegacyFilePath)) return;

    Directory.CreateDirectory(Dir);
    File.Copy(LegacyFilePath, FilePath, overwrite: false);   // 后到的实例在这里抛

    TryCopyLegacyLog("ui.log");
    TryCopyLegacyLog("launcher.log");
    TryCopyLegacyLog("diag.log");

    LoadMigrated = true;                                      // 执行不到这里
}
catch (Exception ex) { LastError = ex.Message; }
```

`LoadMigrated = true` 在 `try` 内、`File.Copy` **之后**。后到的实例在 `File.Copy` 就抛了，直接跳到 catch，所以它的 `LoadMigrated` 是 `false`。**报告描述的「两个都变成 true」不成立。**

真实存在的是**相反**方向的小瑕疵：先到的实例可能只完成复制、还没走完三行日志复制就被某种原因打断，于是它那个实例不提示 —— 那是「少提示一次」，不是「多提示」，配置值在任何情况下都是对的。这个方向我也没有修（影响面是"某次迁移后状态栏没吭声"，代价远小于在迁移路径上加锁）。

## 4. R3：约束本来就在，这轮让它更显眼

报告建议把「RuntimeIdentity.cs 不能用 Core 类型」写进 `AGENTS.md` 或文件头注释。

核对结果：**文件头从 v0.6.0 起就写着**：

> 这个文件会被主程序、Core 与启动器三处**链接编译**（见两个 csproj 的 `<Compile Include>`），因为启动器为了缩小攻击面刻意不引用 Core。因此这里不能用任何需要引用 Core 其他类型的写法。

所以报告这条的措辞（「靠自觉维持」）只说对了一半 —— 约束写过了，只是不够显眼。这轮采纳「更显眼」的部分：

- `AGENTS.md` 新增一节，写明只能用 `System.*`、不能 `using Zephyr.Core.*`；
- 补了一条**可执行的检查**：改完这个文件必须单独构建一次 `Zephyr.Launcher` —— 因为主程序和 Core 都能过的时候启动器可能是坏的，光看整体构建会漏。

同时给 `RuntimeIdentity` 加了 `LegacyProcessName`（R2 需要），并在本轮验证里单独跑了一次 `dotnet build src/Zephyr.Launcher/Zephyr.Launcher.csproj` → 0 警告 0 错误。

`EnsureOpen` 检查 10 秒退避，`Apply` 一进就把 `_lastTryTicks` 重置。报告自己判定「用户主动勾选应立即响应，是好事」「低风险不需改」。

## 6. 顺手修的一处：测试夹具的硬编码路径

报告 §2.1 第 3 条称「测试夹具隔离旧目录时用 `RuntimeIdentity.LegacyDataDirectory`，不再硬编码」—— **这句不准确**，实际是 `"WujieFan"` 字面量。既然本轮已经在动这块，就一并改掉了：

```csharp
public static string LegacyConfigDir => RuntimeIdentity.LegacyDataDirectory;
```

理由写进了注释：夹具要隔离的必须是**产品代码真正会去读的那个路径**，两边各写一份迟早会不一致，而不一致的后果是测试悄悄开始读写用户真实配置（以前就丢过一次）。

改完 254/254 仍然全绿 —— 说明这两个值此前是一致的，这次改动是消除隐患而不是修 bug。

1. **无效探针**：用 notepad 复制成假 `WujieFan.exe` 测进程检测，两次都返回 `False`，差点误判成「检测逻辑坏了」。实际是 notepad 存根立刻退出。**探针返回「没变化」时要先确认探针本身在动。**
