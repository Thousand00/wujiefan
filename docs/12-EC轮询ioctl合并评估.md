# EC 轮询的 132 次 ioctl：能否合并、哪些是协议强制、Read16Stable 有没有更稳的读法

分析对象：`src/Zephyr.Core/Native/PawnIo.cs`、`src/Zephyr.Core/Ec/EcAccess.cs`、
`src/Zephyr.Core/Ec/FanReader.cs`、`src/Zephyr.Core/Ec/EcMutex.cs`。
实测基线沿用 `docs/11-性能开销分析.md`（0.6.3，CPU 0.026% 单核，运行期零文件 I/O，131.7 次/秒其他 I/O）。

## 0. 一句话结论

**这 132 次往返不是"实现写得笨"，而是"驱动给的砖只有单字节"。**
`LpcIO.bin` 只导出了 `ioctl_pio_inb` / `ioctl_pio_outb` / `ioctl_select_slot` / `ioctl_superio_inb|outb|inw`，
没有一个函数接受数组或完成一次完整 I2EC 事务；而每次 `pawnio_execute` 恰好等于一次 `DeviceIoControl`
（`src/Zephyr.Core/Native/PawnIo.cs:117` / `:151`，`C:\Program Files\PawnIO\PawnIOLib.h:50-58` 的签名就是 1 blob 函数 1 次调用）。
所以"在应用层把多次写合并成一次 ioctl"物理上不成立 —— 应用层能减少的只是**读多少个字节**，不是**每次读内部分几步**。

真正可落地、且不碰协议的部分：**顺利路径 132 → 108**（去掉两次生产代码零消费的 PWM 回读），
外加把 `Read16Stable` 的**最坏值**从 492 压到 204（重试 6→3 且跨轮复用 hi，
顺利路径仍是 3 次 Read，防撕裂判据一字不改）。
**"11 字节合并成 1 次 ioctl"只能靠自建复合 blob 实现，代价是接管一份内核态代码 + LGPL 分发义务，不建议做。**

## 1. 先确认基线：132 从哪来（逐行可核）

单次 `Read(ushort)` = **12 次 ioctl**（`src/Zephyr.Core/Ec/EcAccess.cs:130-139`）：

```
Select(0x10)          → 2 outb   (WritePort 0x2E, 索引)
Commit(lo)            → 2 outb   (WritePort 0x2F, 值)
Select(0x11)          → 2 outb
Commit(hi)            → 2 outb
Select(0x12)          → 2 outb   (选数据端口)
WritePort(PortBase, 0x2F) → 1 outb
ReadPort(PortBase+1)  → 1 inb
                        ─────────
                        11 outb + 1 inb = 12
```

`Write(ushort, byte)`（`EcAccess.cs:102-107`）是前 10 次 outb + `Select(0x12)` 的 2 次 + `Commit(value)` 的 2 次
= **12 次 outb、零 inb**。命令次数与 `Read` 完全相同 —— 这条容易被忽略：
**写一个字节并不比读一个字节便宜**，所以"少写"和"少读"在 ioctl 计数上是等价收益。

一次 `FanReader.Read()` = 11 字节 × 12 = **132 次 ioctl**：

| 项目 | 字节 | ioctl | 生产代码是否消费 |
|---|---|---|---|
| 温度 `0x0470`（`FanReader.cs:187`） | 1 | 12 | **是**（过热看门狗、UI、AIDA 发布） |
| 风扇1 `Read16Stable`（`:491`，顺利 3 次 Read） | 2 | 36 | **是** |
| 风扇1 `PwmOut`（`:504`） | 1 | 12 | **否**（见 §4.1） |
| 风扇2 `Read16Stable` | 2 | 36 | **是** |
| 风扇2 `PwmOut`（`:504`） | 1 | 12 | **否** |
| 模式标志 `0x021F`/`0x029F`（`:193`→`:241-254`） | 2 | 24 | **是**（但见 §4.4） |
| 合计 | 11 | **132** | |

## 2. 能否批量合并？——分三个层次，只有第三层能真正做到

### 2.1 应用层排队（伪合并）：不行

很自然会想到"先把 11 次要写的端口值收集起来，再一次性提交"。
但 `ioctl_pio_outb` 的契约就是"写一个字节到某个端口"，一次 `pawnio_execute` 一次 ioctl
（`PawnIo.cs:109-129`，`pawnio_execute(handle, name, in, in_size, out, out_size, return_size)`）。
`return_size` 是**输出**元素数，不是批量入参个数 —— 想靠 `in_size > 2` 传一个数组进去，
blob 的 `ioctl_pio_outb` 只读它需要的那两个 ulong，多余的会被忽略，**命令次数不会减少**。
`PawnIO.cs:151` 的 `ExecuteVoid` 明确要求 `out_size=0`，连输出缓冲都不能复用。

### 2.2 换用 `ioctl_superio_inw`（一次读两字节）：不行，语义不同

`LpcIO.bin` 确实导出了 `ioctl_superio_inw`，看起来能"一次读 16 位"把转速从 36 次砍到 12 次。
但它是**Super-I/O 配置空间的 16 位读**，不是 I2EC 通道的读：I2EC 走的是 `0x2E/0x2F` 的
索引—提交—数据口三段式（`docs/01-现状与技术总结.md:93`），而 tach 的 lo/hi 是两个**独立的
I2EC 地址**（`0x181E` 与 `0x181F`），不是同一地址的高低字节。用 `inw` 读等于换了一套寻址，
读到的不是我们要的数。**不要为了省 ioctl 换原语。**

### 2.3 自建复合 blob（唯一真合并路径）：技术上可行，但不建议

`pawnio_load(HANDLE, const UCHAR* blob, SIZE_T size)`（`PawnIOLib.h:36`）**接受调用方自带的任意 blob，
没有签名/证书参数**。也就是说，做一个导出 `ioctl_i2ec_read(addr) -> byte` 的 blob
（内部一次做完 11 次 outb + 1 次 inb），就能把 **132 次压到 11 次**，理论收益 92%。

但代价是实打实的：

1. **要自己维护内核态代码**。一个 outb 写错端口号，后果不是"读不到数"，是碰别的芯片。
   当前 `EcAccess.cs` 里那 12 步出错只影响一次采样；挪进驱动里出错影响整机。
2. **LGPL v2.1 分发义务**（`docs/01-现状与技术总结.md:141-142`）：自建 blob 必须随包提供
   对应源码与替换方式。
3. **失去上游的可用性背书**。现在的 `LpcIO.bin` 是 PawnIO 官方模块，出问题能对着上游查；
   自建版出问题只有自己。
4. **收益与风险不成比例**。见 §6：省下的是 0.026% CPU 里的一部分，
   而用户可感知的延迟、风扇响应、界面刷新都毫无变化。

**结论：不作为推荐方案。** 如果将来确实要降到"1 字节 1 次 ioctl"，这是唯一路径，
但应当作为独立项目立项、带真机对比测试，而不是顺手改。

## 3. I2C-over-LPC 时序：哪些是协议强制，哪些可以省

按"能不能动"分三档。**注意：这 12 步里 11 步都是 outb，唯一一次数据读取是最后那条 inb。**

### 3.1 协议强制，动了就错（不要碰）

| 步骤 | 为什么强制 |
|---|---|
| `Select(0x10)` + `Commit(loByte)` | I2EC 地址寄存器低字节。不写就等于读上一个地址。 |
| `Select(0x11)` + `Commit(hiByte)` | 地址高字节。少写会读到完全不同的寄存器（0x181E 变成 0x001E）。 |
| `Select(0x12)` | 选数据端口。`0x12` 与 `0x10/0x11` 是三个不同窗口，不能复用。 |
| `WritePort(PortBase, 0x2F)` | 提交/触发。**这一条最容易被误判为冗余**（前面 `Commit` 已经写过 0x2F），但它是"地址已设好 → 请 EC 输出数据"的握手。省略它在部分固件上仍能读到值，在另一些上会读到上一次的残留字节 —— 属于"改完可能还能跑，但正确性不再有保证"。**不要省。** |
| `ReadPort(PortBase+1)` | 真正取数。 |
| 端口基址 `0x4E` | `0x2E` 在本机型实测读到垃圾值（`docs/01-现状与技术总结.md:92`）。 |
| 整段时序包在 `EcMutex` 里 | 一次采样 = 十几条端口写，别人的 I2EC 时序插进中间就是错值。`FanReader.cs:167-180` 的注释已经把后果写清楚了（温度会进过热看门狗）。 |

### 3.2 语义上可省，但省了要有产品决策

| 步骤 | 可省的理由 | 代价 |
|---|---|---|
| 两次 `PwmOut` 回读（24 次，18%） | `FanSample.PwmOut` → `PwmPercent` 在 `src/` 里**零消费**（grep 确认，只有 `FanSample.cs:27-31` 定义与测试/实验工具在用） | 测试与 `tests/EcReadSmoke`、`tests/FanControlLab` 要显式打开开关 |
| 模式标志每拍都读（24 次） | 模式只在用户切档时变，1 Hz 全量重读是浪费 | 若降频到 1/5 拍，界面模式显示最多滞后 5 s；退出时的 `ReadModeState()` 是独立路径，不受影响 |

### 3.3 只在"读失败/撕裂"时才触发的，可以改最坏值

`Read16Stable` 的重试循环。见 §5。

## 4. 具体改法与收益（按性价比排序）

### 4.1 【推荐】给 `Read()` 加"是否回读 PWM 输出"开关，默认关

- 位置：`src/Zephyr.Core/Ec/FanReader.cs:489-506` 的 `ReadFan`，
  `:504` 的 `PwmOut = _ec.Read(pwmOutAddr)` 改成受构造函数/`Read(bool readPwm)` 控制。
- 为什么不直接删：`PwmPercent` 是测试与实验工具在用的公开语义
  （`FanSample.cs:27`）。删字段会让 `tests/Zephyr.Core.Tests/FanSampleTests.cs`、
  `tests/Zephyr.Core.Tests/FanReaderSamplingTests.cs`、`tests/EcReadSmoke/Program.cs`、
  `tests/FanControlLab/Program.cs` 编译不过 —— 这四个文件都引用了 `PwmOut`/`PwmPercent`（已 grep 确认）。
- 收益：**132 → 108（−18%）**，每轮少 24 次 ioctl。
- 风险：极低。界面、RTSS 覆盖层、AIDA 发布、看门狗都不读 `PwmPercent`（已 grep 确认）。
- 测试：`FakeEc` 已记录 `Reads`，加一条"默认不读 0x1809/0x1804"的断言即可锁住。

### 4.2 【推荐】`Read16Stable` 跨轮复用上一次的 `hi`：不降强度、白白省 1 次 Read/轮

现在的循环每轮都完整读 `hi1, lo, hi2` 三次。但**上一轮的 `hi2` 就是下一轮的 `hi1`**
（时间上离下一轮的 `lo` 只差一次读，判据强度完全不变）：

```csharp
int hi1 = Read(hiAddress);                 // 只读这一次
for (int attempt = 0; attempt < 6; attempt++)
{
    int lo = Read(loAddress);
    int hi2 = Read(hiAddress);
    last = (hi2 << 8) | lo;
    if (hi1 == hi2) { stable = true; return last; }
    hi1 = hi2;                             // 复用, 不再重读
}
```

- 收益：顺利路径 **3 次 Read 不变**（36 ioctl 不变，无需改动热路径）；
  最坏 6 轮从 **18 次 Read 降到 13 次**（`hi1` 一次 + 6 轮 × 2 = 13）。
  折成 ioctl：单扇 216 → **156**，两扇叠加整拍 **492 → 348**。
- 风险：**低，但要论证清楚**——`hi2` 之后到下一轮 `lo` 之间没有别的 EC 写操作，
  所以"上一轮结束时刻的 hi"和"新一轮开始时刻的 hi1"之间不会插入我们的写；
  但**别的进程**（HWiNFO/LHM）如果在 `Release()` 之后插进来，下一轮 `hi1` 就不该复用。
  因此这个改法必须配一句：**只在同一把锁的同一次 `Read16Stable` 调用内复用** —— 也就是上面代码
  本来就是这个范围（循环体全在锁内），安全。
- 测试：`FakeEc.Read16Stable` 目前是桩（`FakeEc.cs:82-87`），不模拟撕裂，
  **改之前必须先把它改成模拟"hi 撕裂 → 收敛"**，否则改动无测试覆盖。

### 4.3 【可选】重试上限 6 → 3

- 撕裂需要"读 lo 与读 hi 之间恰好借位"，1 Hz 采样下是罕见事件；
  **连续 6 轮全撕裂**意味着总线已经在出问题，此时返回 `stable=false` 让上层丢弃
  比继续重试更诚实。
- 收益：单扇最坏从 18 次 Read 降到 **7 次**（`hi1` 一次 + 3 轮 × 2），
  即 216 → 84 ioctl；配合 4.2 后整拍最坏 **348 → 204**。
- 风险：中低。会略微提高"本拍判为不稳定"的概率（极罕见场景）。
  若担心，可保留 6 轮但**加一个总时间预算**（例如从进入函数起 2 ms 就放弃）。

### 4.4 【可选】模式标志降频读取

- 收益：模式标志 2 字节/拍 = 24 次。降到每 5 拍读一次，**平均**省 19 次/秒
  （132 → ≈113）；完全只在"用户切档后 1 拍内"读，则稳态 132 → 108。
- 风险：中。若改成"只在切档后读"，需要额外记住切档时刻，且
  **EC 自己会在约 1.5 秒内把非 0xDC 的模式回写覆盖**（`docs/01-现状与技术总结.md:120`），
  不周期性回读就看不出"EC 把我的模式改回去了"——这恰恰是当前实现要抓的东西。
  **因此更保守的做法是降频到 1/5，不要改成事件驱动。** 这是产品决策，不是纯技术改动。

### 4.5 【最低优先级】复用 `ulong[]` 缓冲，消掉 275 个短命数组/轮询

- `PawnIo.cs:113-114` / `:126-127` / `:147-148` 每次调用都 `new`。
- 收益：GC 压力从"看不见"变成"更看不见"（全 gen0，不进私有提交）。
  **对 CPU 数字基本无影响**，`docs/11` 已经算过。
- 只有在做 4.1–4.3 **之后**才值得顺手做，否则纯属增加改动面。

## 5. `Read16Stable` 最坏 3.7× 放大：有没有更稳的读法

### 5.1 当前顺序 `hi → lo → hi` 是**正确的**，不要改

反直觉但重要：tach 是**递减**计数器，RPM = 2156250 / count。
撕裂只会发生在"读 lo 与读 hi 之间该字节发生了借位/回绕"。
`hi1 == hi2` 恰好证明"在这两次读 hi 之间，hi 没动过，所以中间读到的 lo 与它同属一个计数周期"。

**不要换成 `lo → hi → lo`**：那样只能证明 lo 没变，而 lo 正是回绕时剧烈变化的那一半，
`lo1 == lo2` 在递减计数器上反而**不能**排除 hi 已借位 —— 会把撕裂值当成稳定值返回，
正是 `EcAccess.cs:145` 注释里警告的"撕裂值恰好落在看起来正常的区间"。

### 5.2 真正的改进是"少重试"，不是"换判据"

按 §4.2 + §4.3：顺利路径 3 次 Read 不变（正确性保护强度一字不改），
最坏从 18 → 13 → 7 次 Read。**这就是最稳的读法：不牺牲判据，只压缩最坏。**

### 5.3 一个不要做的"优化"

不要用"两次读 hi 取较小值/较大值"来猜真实值。递减计数器下看起来有单调性可用，
但**计数器在 EC 固件里可能被重置**（换档、风扇停转瞬间），猜错方向会给出
一个"看起来合法"的错误转速 —— 而错误转速会进 UI、RTSS 覆盖层、AIDA 发布。
宁可返回 `stable=false` 报"读取不稳定"，也不要猜。

## 6. 预期收益（老实说：对用户不可感知）

| 方案 | 顺利路径 | 最坏路径（两扇） | 对 CPU 的影响 |
|---|---|---|---|
| 现状 | 132 | 492 | 0.026%（实测） |
| 4.1 PwmOut 开关 | 108 (−18%) | 468 | ≈0.021% |
| 4.1+4.2 | 108 | 348 | ≈0.021% |
| 4.1+4.2+4.3 | 108 | 204 | ≈0.021% |
| 4.1+4.2+4.3+4.4（降频 1/5） | ≈89（均值） | ≈185 | ≈0.018% |
| 自建复合 blob | 11 (−92%) | 41 | 未知，需实机测 |

（最坏值口径：两扇各自最坏之和；`Read16Stable` 走完重试才放弃时
单扇 18 次 Read = 216 ioctl，两扇 432，加上温度/PWM/模式 60 = 492。）

**必须说清楚的一点**：用户实测 CPU 0.026% 单核、零文件 I/O，说明
**当前实现根本不是性能问题**。以上改动的真实价值是三条，没有一条是"省 CPU"：

1. **降低最坏单拍耗时**（撕裂时的 216 次 ioctl ≈ 0.5–1.1 ms），让"拿锁后卡住"的窗口更可预测；
   顺带降低与 HWiNFO 抢 `Global\Access_EC` 时的占用时长。
2. **减少内核往返次数**，对整机是礼貌（131.7 次/秒的其他 I/O 计数会掉到 ~110）。
3. **去掉生产代码不消费的读取**，让"每拍做 132 件事"这个数字不再吓人。

如果目标是"让用户觉得更流畅"，这些都不必要 —— 该改的是别的东西。

## 7. 明确不能做的改动（动了就危及读取正确性）

1. **不要去掉 `hi1 == hi2` 判据或退化成单次读。** 撕裂值可能落在合法区间（`EcAccess.cs:145`）。
2. **不要改成 `lo → hi → lo`。** 递减计数器下这个判据是反的（§5.1）。
3. **不要在没有并发/重入保护的情况下读 EC。** `EcMutex` 必须覆盖整次采样
   （`FanReader.cs:167-180`、`EcMutex.cs:105-142`）；"只读所以不用锁"是错的。
4. **不要省掉 `Select(0x12)` 之后那次 `WritePort(PortBase, 0x2F)`。** 省了可能还能跑，
   但正确性不再有保证（§3.1）。
5. **不要把 `0x4E` 换成 `0x2E`。** 实测读到垃圾值（`docs/01-现状与技术总结.md:92`）。
6. **不要用 `ioctl_superio_inw` 读 tach。** 寻址语义完全不同（§2.2）。
7. **不要给 `ExecuteVoid` 传 `out_size=1`。** 会读到残留内存，历史上被解释成
   `"ioctl_se"` 的字节（`PawnIo.cs:138-142`）。
8. **不要为了省 ioctl 把读拆到多个线程并发执行。** EC 是串行总线，
   并发只会让两边都读到撕裂值。
9. **不要删 `FanSample.PwmOut` / `PwmPercent`。** 测试与实验工具在用；用开关降频，不要删字段。
10. **不要在 `stable == false` 时返回"看起来合法"的值而不标记。**
    上层靠 `note = "读取不稳定(已丢弃本次计数)"`（`FanReader.cs:495`）决定丢弃。

## 8. 如果要做，建议的落地顺序

1. 先改 `FakeEc.Read16Stable`，让它能模拟"撕裂 → 重试 → 收敛"和"持续撕裂"两种场景
   （现在是桩，`FakeEc.cs:82-87`）。**没有这一步，4.2/4.3 都是裸改。**
2. 做 4.1（PwmOut 开关）+ 4.2（跨轮复用 hi），跑 `pwsh -NoProfile -File tools/verify.ps1 -FailOnSkip`。
3. 用 `tests/EcReadSmoke` 在真机上对比改前/改后的 ioctl 次数与读数一致性
   （同一台机器、同一负载下连采 100 次，转速差异应低于既有抖动 1%）。
4. 4.3 / 4.4 视用户对"最坏值"和"模式显示滞后"的接受度再定。
