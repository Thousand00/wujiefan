## 2. 补上的三个测试缺口

都在 `tests/Zephyr.Core.Tests/`，不改生产代码。每条都做了变异验证 —— 只有变异后测试真变红，才能说明这条断言「有牙」。

### G1 · `EcMutex` 销毁后再取用

```csharp
// tests/Zephyr.Core.Tests/EcMutexTests.cs
public void 销毁之后再取用_返回false()
```

钉住 `Acquire` 开头那句 `if (_disposed) return false;`。删掉它，另一个线程会去 `Wait` 一批已经 `CloseHandle` 的句柄。

顺带覆盖了「重复 Dispose 必须安全」——退出路径上 `Dispose` 确实会被调两次。

**变异验证**：删掉 `_disposed` 检查 → `销毁之后再取用_返回false` 立刻红，`Assert.False() Failure / Expected: False / Actual: True`。还原后通过。

### G2 · 半持有回滚

```csharp
public void 拿不全时不能留下半持有的锁()
```

这个缺口比报告描述的更值得钉住。`EcMutex.cs:96-99` 的注释记着早先的真实故障：留着部分持有的句柄返回 false，调用方据此跳过 `Release`，于是 `Global\Access_ISABUS` 被本进程长期占住，HWiNFO / LHM 再也读不到 EC —— 而本程序一切正常，没有任何日志指向这里。

做法：一个线程独占第二把锁，被测实例 `Acquire` 必然「拿到第一把、拿不到第二把」；然后断言**第一把已经还回去了**（换一个新线程去拿，必须拿到）。

**变异验证**：删掉 `RollbackTo(depthBefore)` → 测试红在「换线程拿第一把」那一句，`Actual: False`。还原后通过。

### G6 · 迁移失败的信号不能被 Save 冲掉

```csharp
// tests/Zephyr.Core.Tests/SettingsMigrationTests.cs
public void 迁移失败的信号不会被之后一次Save冲掉()
```

`AppSettings.LoadMigrateError` 是 static 字段，`JsonSerializer` 默认不序列化 static 成员，所以 `Save()` 碰不到它 —— 这条断言钉的正是这个「靠不序列化才成立」的巧合。`Load()` 之后程序自己会保存好几次（切模式、改自启、托盘操作），任何一次把它清掉，用户就永远看不到「旧设置没搬过来」。

除了「Save 之后仍在」，还断言落盘内容里**不出现**这个键名 —— 一旦写进配置文件，下次 `Load` 读到的就是上一次的旧错误。

**变异验证**：在 `Save()` 成功分支插一行 `LoadMigrateError = null;` → 测试红，`Expected: "The target file ..." / Actual: null`。还原后通过。

## 3. 没补的三个缺口，以及为什么

这三条都不是「不值得补」，而是**落地要改生产代码的可见性或形状**，我判断收益不抵这个改动本身的风险。

### G3 · `AutoStartManager.Run` 的超时顺序

`Run` 是 `private static`，`AutoStartManager` 也是 `sealed`。要测它得二选一：把 `Run` 改成 `internal`（引入 `InternalsVisibleTo`，本项目至今没有），或者抽一个 `IProcessRunner` 依赖注入进去。

而且这条测试要**注入一个永远不关闭 stdout 的进程**。在单测里长期持有一个「会卡住的子进程」，比它要防的那个 bug 更容易变成新的不稳定源 —— 尤其在 CI 与本地共用同一台机器的情况下。

**替代保障**：那段代码有 12 行注释解释「为什么必须先 `WaitForExit` 再读流」「为什么两条流必须异步读」，`Act` 与 `Assert` 意图都写在代码旁边。我倾向于保持现状，等哪天真的要改这段逻辑时再连测试一起补。

### G4 · `HtmlDecode` 路径含 `&`

同样卡在 `QueryTask` 是 `private`，而且它直接调 `Run("schtasks.exe", ...)` —— 要测就得真跑 `schtasks`。`QueryTask` 的输入是真实计划任务 XML，没有可注入的字符串入口。

**这个缺口我认，但它的失败模式是可观测的**：`&` 没解回来 → 自家任务被判成外来任务 → 界面显示「同名任务已存在, 已锁定」，自启动开关变灰。用户当场就能看见，不是静默故障。

### G5 · `EnsureSingleRestore` 两次调用只执行一次

`FanModeController` 在 `src/Zephyr/Ui/`，测试工程只引用 `Zephyr.Core`，够不到这个类。本轮之前它已经在没有测试的情况下拦住了真实缺陷（0.6.0 前「退出时对 EC 写了两次自动」），说明这条守卫的语义在代码注释里写得足够清楚：

> 这个标志同时挡住 ExitApplication → Dispose → RestoreAutoOnShutdown 的重复写入，任何一处改错都会让退出时对 EC 多写或少写一次，而这两种错都不会有人报上来。

## 7. 我自己的失误

**第一条 G6 测试写错了。** 第一版沿用「在配置路径上建一个同名目录」来制造迁移失败，然后在同一路径上调 `Save()` —— 目录还在，`Save` 当然失败，测试红在「当文件已存在时，无法创建该文件」。

这不是被测代码的问题，是我把「制造失败」和「验证 Save 成功」两个阶段放在同一个环境里了。修法是在 `Load()` 之后、`Save()` 之前把那个目录删掉 —— 现实里也是这个顺序：迁移那一刻没写成，之后程序照常跑、照常保存。

**教训**：用「制造环境故障」的手法测异常路径时，测完要把故障拆掉再做后续的正常路径断言；否则测的是故障本身，不是被测逻辑。
