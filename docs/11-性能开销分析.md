# 性能开销分析（0.6.3 实机实测 · 0.7.0 处置记录）

分析对象：`E:\tools\Zephyr` 装好的 0.6.3，pid 10592，2026-11-25 19:26:33 启动，
分析期间窗口**完全收在托盘里**（`MainWindowHandle=0`），所以下面的数字里没有任何界面绘制成分。

## 一句话结论

**唯一主要开销是每轮询 132 次 PawnIO 内核驱动往返（约 132 次/秒），
其他所有维度都可以忽略：运行期文件读写增量为 0，CPU 占单个核心的 0.026%，
内存没有泄漏（私有提交字节全程不涨）。**

## 实测数据

60 秒精确窗口（`Win32_PerfRawData_PerfProc_Process` + `Get-Process`）：

| 指标 | 实测 |
|---|---|
| CPU 时间增量 | 0.016 s / 60 s = **0.026% 单核** |
| 文件写操作增量 | **0**（累计 2 次，全是启动期） |
| 文件读操作增量 | **0**（累计 64 次 / 1,250,505 B，全是启动期） |
| 其他 I/O 增量 | **131.7 次 / 秒**（累计 1,163,300 次 / 2h27m） |
| 工作集增量 | +0.76 MB，但见下「不是泄漏」 |
| 私有提交增量 | +0.03 MB（27.03 → 27.06，基本不动） |
| 句柄增量 | +4（且长期锯齿，见下） |

## 开销明细：132 次驱动往返从哪来

单次读 1 字节 EC 寄存器 = **12 次 `DeviceIoControl`**：

```
Select(0x10) → Commit(lo) → Select(0x11) → Commit(hi) → Select(0x12)
→ WritePort(PortBase, 0x2F) → ReadPort(PortBase+1)
```

（`src/Zephyr.Core/Ec/EcAccess.cs:130-139`，`Select`/`Commit` 各 2 次 outb）

一次完整轮询 `FanReader.Read()`（`src/Zephyr.Core/Ec/FanReader.cs:160-212`）：

| 项目 | 字节 | 驱动调用 |
|---|---|---|
| CPU 温度（1 字节） | 1 | 12 |
| 风扇1 转速 `Read16Stable`（3 次 Read） | 2 | 36 |
| 风扇1 PWM 输出回读 | 1 | 12 |
| 风扇2 转速 `Read16Stable`（3 次 Read） | 2 | 36 |
| 风扇2 PWM 输出回读 | 1 | 12 |
| 模式标志（2 字节） | 2 | 24 |
| **合计** | **11** | **132** |

按单次 ioctl 2–5 µs 估算 ≈ **0.3–0.7 ms/轮询**，占 1000 ms 周期的 0.03–0.07%，
与实测算出的 0.026% CPU 同一量级 —— 这条链路就是全部开销。

## 0.7.0 实际做了什么

下面这份分析写于 0.6.3。0.7.0 按它和四路专家评审的结论落地了四项，**结论先说：稳态 CPU 本来就只有 0.026% 单核，所以这些改动省下的算力可以忽略；真正的收益是把最坏延迟压下来、把「争用」和「设备坏了」分开，以及砍掉 30% 的内核往返。**

| 改动 | 效果 | 依据 |
|---|---|---|
| 砍掉 CPU 温度读数 | 每轮 **−12 次**驱动往返 | 用户决定：连过热保护一起废弃 |
| 生产路径关掉 PWM 回读 | 每轮 **−24 次**（132 → 96，−27%） | 下文 §1 |
| EC 争用不再算作设备失效 | 不再有「争用→重连→清零→再争用」自转 | 专家评审 P1 |
| 重连补上退避闸门 | 设备真坏时不再每 5 秒重建一次 | 专家评审 P1 |
| 漂移判定补 2 秒时间地板 | 高轮询频率下不再一次抖动就交还 | 专家评审 P1 |
| 每 60 拍记一行 p50/p99 耗时 | 以后「卡不卡」有数据，不用靠猜 | 专家评审建议 |

**没有做的**（评估过，明确不采用）：

- **把 132 次 ioctl 合并成一次**。`LpcIO.bin` 的导出表里没有接受数组或整段 I2EC 事务的入口，每次 `pawnio_execute` 恰好等于一次 `DeviceIoControl`；要合并只能自建内核态 blob，那会带来内核模块的分发与签名负担，为 0.026% 的 CPU 不值得。详见 `docs/12`。
- **`Read16Stable` 从 6 轮减到 3 轮**。顺利路径本来就 3 次就返回，省的是 0；而撕裂最可能发生在转速变化最快时（正是强冷满转），砍掉一半纠错余量换不到任何东西。
- **复用 `params ulong[]` 的缓冲**。收益是 GC 压力，而 GC 压力本来就看不见；风险是缓冲区要跨托管/非托管边界交给委托，还可能被并存的第二个 reader 串用。
- **定时器改型 / 消除每帧分配 / `Marshal.Copy` 改多次写**。都是 2% 以下的账，而每一项都要动已经用实测数据锁住的代码（见 `AidaSharedMemory.cs:98-112` 的注释）。
- **模式标志改事件驱动**。EC 会在约 1.5 秒内把非 `0xDC` 的模式回写覆盖，周期回读正是要抓这个，改成事件驱动就看不见了。

## 三个可以省的地方（按价值排序，0.6.3 原文）

### 1. 两次 PWM 输出回读（24 次驱动调用，全轮询的 18%）

`src/Zephyr.Core/Ec/FanReader.cs:504` 的 `PwmOut = _ec.Read(pwmOutAddr)` 每轮都读，
但 `PwmOut` 在**生产代码里零消费**：`FanSample.cs:31` 只是 `Math.Clamp` 一下算成
`PwmPercent`，而这个属性在 `src/Zephyr/Ui` 里一次都没被读过（grep 确认）。
真正用它的是测试与实验工具（`tests/EcReadSmoke`、`tests/FanControlLab`、
`FanReaderSamplingTests`、`FanSampleTests`）。

**省这 24 次不影响任何功能** —— 但 `PwmPercent` 是测试在用的公开语义，
所以正确改法不是删字段，而是给 `Read()` 加一个「要不要读 PWM 输出」的开关。
**0.7.0 的落地方式：参数默认 `true`（测试与实验工具一行都不用改），生产路径 `FanPollingController` 显式传 `false`。** 反过来做（默认关）会让`FanReaderSamplingTests` 里那条「PWM 越界值要夹到 100%」的断言直接失败。

### 2. `Read16Stable` 最坏 3.7× 放大

`src/Zephyr.Core/Ec/EcAccess.cs:147-165` 的重试循环
`for (attempt < 6) { hi1=Read(hi); lo=Read(lo); hi2=Read(hi); if (hi1==hi2) return; }`
顺利时 3 次 Read，**最坏 6 轮 = 18 次 Read = 216 次驱动调用**（两扇叠加后整轮 492 次）。

顺利路径下不是问题；只在风扇转速跳变、高低位撕裂时才触发重试。
配合方案 1，最坏情况能从 492 降到 444。属于「顺手降最坏值」，不是必须。

### 3. 每轮询 8–9 KB 的短命数组

`src/Zephyr.Core/Native/PawnIo.cs:113-114/126-127/147-148` 每次 `Execute*` 都
`new ulong[...]`，加上 `params ulong[]` 让每个调用点都新建数组：
121 次 outb × 2 个 + 11 次 inb × 3 个 ≈ **275 个数组/轮询**。
全部是 gen0，1 Hz 下约 31 MB/小时但**全部在 gen0 回收，不进私有提交**
——这正是「私有提交字节不涨」的原因。可以用线程静态缓冲区复用，收益是减少 GC 压力，
但当前 GC 压力已经看不见（CPU 0.026%），**优先级最低**。

## 内存：没有泄漏

20 分钟趋势（30 秒采样一次）：

```
21:39  WS=63.50  Priv=27.03  Handles=419
21:45  WS=66.51  Priv=27.03  Handles=451   ← 爬到顶
21:46  WS=61.82  Priv=27.06  Handles=403   ← 掉回去
21:50  WS=64.79  Priv=27.03  Handles=429   ← 又爬
```

**工作集和句柄都是锯齿**（WS 振幅约 5 MB、周期约 10 分钟；句柄 403↔451 来回），
而**私有提交字节从头到尾锁在 27.03–27.06 MB**。如果是泄漏，私有提交必然单调上涨。

之前 0.5.x 记过的「6 分钟内 WS 持续涨 10 MB、疑似每小时泄漏 31–60 MB」，
现在看就是同一段锯齿的上升沿被截取成了短样本 —— **那个结论不成立，可以划掉**。

句柄锯齿属于 .NET 运行时/GDI 句柄缓存的正常行为，池已核对：
`NonPagedSys 0.04–0.05 MB`、`PagedSys 0.51 MB` 全程恒定。

## I/O：运行期零写入

`UiLog`（`src/Zephyr/Program.cs:23-57`）只记异常不记常规轨迹，单文件上限 64 KB；
`AppSettings.Save()` 的 8 个调用点全是事件驱动（切模式、改设置、退出），
不在轮询路径上。实测印证：**文件写累计 2 次、616 字节，从启动到现在一次没变。**

`AidaSharedMemory` 的映射只在 `Open()` 建一次，写共享内存走的是 `Marshal.Copy`
到已映射视图，不产生文件 I/O —— 这也是「其他 I/O 132 次/秒」里不含字节量的原因
（每次 440 B/5s 是驱动调用的附带记账，不是磁盘写）。

## UI：不在热路径上

分析期间窗口不可见（托盘），但即使可见，绘制也已经做了防抖：

- `DataCard.Value` 值没变就 `return`，不 `Invalidate()`（`Controls.cs:49`）
- `SetMeterRaw` 变化小于 0.05% 不重绘（`Controls.cs:74-79`）
- 所有 `Pen`/`SolidBrush`/`GraphicsPath` 都在 `using` 里，`Region` 换新前先 `Dispose()`
  （`MainForm.cs:227-229`）

## 实测方法（可复现）

脚本见 `_perf/`（分析完已删）。要点：

- **`Get-Process` 的 `ReadOperationCount`/`WriteOperationCount`/`ReadTransferCount`
  在 .NET 9 下读不到**（全是 null），必须走
  `Get-CimInstance Win32_PerfRawData_PerfProc_Process` 的
  `IOReadOperationsPerSec` / `IOWriteOperationsPerSec` / `IOOtherOperationsPerSec`
  —— 名字带 PerSec，语义是**累计计数**，要两次采样做差。
- `Win32_PerfRawData_NETFramework_NETCLRMemory` 只有 `_Global_` 一个实例，
  **拿不到指定进程的 GC 分代数据**。
- 从外部进程 `OpenProcess` 拿提权进程句柄再 `GetGuiResources` 会返回 0/0，
  GDI/USER 计数只能在进程内部取。
