## 1. 它建议的两条 AGENTS.md 护栏

报告第 7 节建议加两条：

- **(a)** 不要碰 `AutoStartManager.Run` 的读流/超时顺序。
- **(b)** 不要给 `AppSettings.LoadMigrateError` 加 `[JsonProperty]`。

**(a) 采纳**。核对过 `src/Zephyr.Core/Config/AutoStartManager.cs:575-577` 那段注释确实在 `WaitForExit(15000)`（`:581`）之前，写的是真实的失败模式：同步 `CopyTo` 读到 EOF 才返回，子进程卡住且不关 stdout 时它永不返回，超时形同虚设、UI 线程无限卡住。已按这个意思写进 `AGENTS.md` 安全红线，并点明「那段 12 行注释就是这次故障的复现说明」。

**(b) 采纳结论、但不照抄理由 —— 它说的机制是错的。**

报告写「如果未来有人给它加 `[JsonProperty]`，Save 的读写循环就会把它覆盖成 null」。我实测了这件事，static 成员根本进不了序列化，加什么都一样：

| 变体 | 序列化输出 |
|---|---|
| `[JsonInclude] public static string? M { get; set; }` | `{"A":1}` |
| `[JsonInclude] public static string? M;`（配 `IncludeFields = true`） | `{"A":1}` |
| `[JsonPropertyName("LoadMigrateError")] public static string? M { get; set; }` | `{"A":1}` |

三条都不含 `M`。（`System.Text.Json` 不序列化 static 成员，这是类型系统层面的，特性改不了。）

真正会让它被冲掉的是**把 static 去掉、改成实例属性**。我顺手把这条也测了：实例属性只带 `private set` 时会被正常序列化并在反序列化时被读回 ——

```
json={"A":1,"M":"err"} | back.M=err
```

也就是说：`Save()` 写出的 JSON 里会带上 `LoadMigrateError`，下次 `Load()` 读到的就是上次那份旧错误，用户会以为这次迁移又失败了。这才是真实的失效路径。

所以 `AGENTS.md` 里那条护栏我按实测机制写：**必须留在 static 上**，并注明「`[JsonInclude]`/`[JsonPropertyName]`/`IncludeFields` 都试过都不行，已实测确认」，失效路径写「改成实例属性就会进 JSON」。如果照抄报告的措辞，护栏会指向一条不会发生的操作，而真正该防的改动（去掉 static）反倒没被写进去。

顺带确认当前实现与这条护栏一致：`src/Zephyr.Core/Config/AppSettings.cs:145` `public static string? LoadMigrateError { get; private set; }`；`Save()` 成功分支只做 `LastError = null;`（`:398-399`），不碰它；`Load()` 开头统一清空六个诊断位（`:173-178`）。

## 3. 它引用但没有实跑的部分

报告自己声明沙箱无 dotnet SDK，回归用 grep 替代。这是诚实做法，但它据此说「回归通过」的边界比我上一轮窄：

- 它验的是「生产代码零改动 → 上一轮约束不可能被破坏」，这个推理成立。
- 它**没有**验「新增的三条测试真的能跑通」。而这三条测试的通过/失败我是实跑过的：257/257，`tools/verify.ps1` 5/5、EXITCODE=0。
- 它**没有**验变异后的红。变异验证是我在能跑 dotnet 的环境里做的，三次都红了（`Expected: False / Actual: True`、`Expected: True / Actual: False`、`Expected: null / Actual: "The target file..."`）。

所以「回归通过」这句成立，但成立的依据是「生产代码没变」+「测试实跑在别处验过」，不是它自己的 grep。报告对此的表述是准确的（明确写了沙箱限制），没有夸大。

## 4. 阶段 3 里一条措辞值得记下来

报告对 G1 变异的描述：「删掉挡板后第二把锁可能在 `CloseHandle` 后被释放、第一把 Wait 因其他线程已释放而成功」。

这里它在推测 Win32 的具体返回值，而它自己也写了「Win32 文档未保证具体返回值」。实际变异结果我这边是确定的：删掉 `if (_disposed) return false;` 后测试红在 `Assert.False(mutex.Acquire(100))`，`Expected: False / Actual: True` —— 也就是 `Acquire` 在已 Dispose 的实例上返回了 true。

它把结论落在「变异机制可信」上，没有拿推测当证据，这个处理是对的。记在这里只是提醒：**这类「删掉之后会发生什么」的推理不要写成事实**，除非真的跑过。
